# Проверенные исправления клиента gpupdate в ALT

`08-gpupdate-client-fixes.yml` — отдельный плейбук подготовки одного ALT-ПК.
Он устанавливает отсутствующие пакеты `gpupdate`/`alterator-gpupdate` и применяет
три проверенные поправки клиента. В штатном Setup используется та же роль:
сразу после установки пакетов до join и повторно перед первым применением GPO.
Сам плейбук не вводит компьютер в домен, не запускает gpupdate, не меняет GPO
и не перезапускает пользовательский сеанс.

Поддерживаются проверенные пары `gpupdate`/`gpoa-lib` **0.16.1-alt1** и
**0.16.4-alt1**. Смешанные версии двух пакетов не принимаются. Проверяются
владелец RPM, версия, права и точные SHA-256 модулей. Уже исправленные модули
принимаются без записи. Неизвестная
версия или другое содержимое останавливают весь перенос до первого изменения;
нельзя отключать эту проверку, чтобы применить поправки к новой версии пакета.

Исправления:

- `gpoa/gpt/services.py`: чтение `serviceAction` через существующий `set_servact`;
- `gpoa_lib/frontend/kde_applier.py`: отложенное определение KDE, Qt offscreen,
  инструменты KF5/KF6 и отказ от угадывания версии при смешанной установке;
- `gpoa/frontend/shortcut_applier.py`: сохранение типа, значка, комментария,
  UID, disabled и lifecycle-флагов машинных ярлыков в пользовательском контексте.

В 0.16.4 исправления KDE и переноса ярлыков включены производителем: эти файлы
проверяются по отдельным исходным SHA-256 и не переписываются. Дополнительно
проверяется `gpoa/gpt/shortcuts.py`, в котором находится используемый frontend
метод `from_machine_dict`. Применяется только прежняя поправка setter в
`services.py`. Повтор после применения возвращает `changed=false`.

## Отдельный запуск

Используйте существующий доверенный SSH inventory и ровно один выбранный ПК.
Плейбук отклоняет выбор нескольких машин до установки пакетов или поправок.
Не используйте старое задание Setup для запуска этого обслуживания.

```bash
cd /home/altserver/ansible
ANSIBLE_CONFIG="$PWD/ansible.cfg" ansible-playbook \
  -i /path/to/trusted-inventory \
  playbooks/08-gpupdate-client-fixes.yml \
  --limit alt-zhkh2-pc1 --check

ANSIBLE_CONFIG="$PWD/ansible.cfg" ansible-playbook \
  -i /path/to/trusted-inventory \
  playbooks/08-gpupdate-client-fixes.yml \
  --limit alt-zhkh2-pc1
```

`--check` проверяет и прогнозирует исправления, не меняя модули и не создавая
состояние блокировки/резервных копий. Если пакет ещё не установлен, сначала
нужна его реальная установка: прочитать отсутствующие модули в check mode нельзя.
Обычный повторный запуск на исправном клиенте возвращает `changed=false`,
`backup_id=null`, а каждый элемент `fixes` имеет `state=already_fixed`.

При активном gpupdate или пакетном менеджере запись откладывается: роль делает
ограниченные повторные попытки только для `client_busy`, затем останавливается.
Она не завершает процессы и не отключает службы. После обновления пакетов
повторите проверку; новую исходную версию нужно проверить отдельно и добавить
как новую поддерживаемую версию, если поправки ещё нужны.

## Резервная копия и откат

До первой записи планируются все модули. Изменяемые исходные файлы, их метаданные,
`manifest.json` и автономный `rollback.py` сохраняются на клиенте в закрытом
каталоге `/var/backups/alt-gpupdate-compat/<backup_id>/`. Точный ID выводится в
`alt_gpupdate_compat_result`. Запись модулей атомарная. Ошибка записи вызывает
проверяемый откат уже изменённых модулей; непроверенный откат означает остановку
и необходимость разбора, а не успешное исправление.

Для сознательного возврата к исходным модулям на клиенте:

```bash
sudo /usr/bin/python3 \
  /var/backups/alt-gpupdate-compat/EXACT_BACKUP_ID/rollback.py \
  --rollback EXACT_BACKUP_ID
```

Новые manifests (schema=2) сохраняют пакет и версию каждого изменённого модуля.
Старые manifests (schema=1) продолжают означать только исходную 0.16.1; они не
разрешают откат после обновления пакета. Откат проверяет все файлы, версии
пакетов, резервные байты и метаданные до первой
записи. Более поздние изменения не перезаписываются. Возвращаются исходные
модули, поэтому вместе с ними могут вернуться исходные ошибки gpupdate.

## Приёмка

На копиях исходных модулей проверяются применение, повторный запуск, ошибки
записи и откат. Затем отдельно запускаются `--check` и два обычных прогона
на выбранном ПК. Для уже исправленного пилота ожидается отсутствие изменений
в действующих модулях. После плейбука оператор отдельно проверяет машинный
gpupdate и пользовательский `gpupdate-user.service` в существующем сеансе,
журналы ошибок и результат нужных GPO. Нулевой код самого плейбука не заменяет
эту функциональную проверку.
