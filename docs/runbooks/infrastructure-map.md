# Карта инфраструктуры

Раздел «Сеть и диагностика → Инфраструктура» читает готовый снимок. Веб, API `GET /api/v1/network/infrastructure` и инструмент MCP `openvpn_network_infrastructure` используют один формат. Для браузера действуют обычные права просмотра сети. Для API и MCP нужен токен с `network:read`.

Общая карта включает все узлы снимка, в том числе ВМ и контейнеры без привязки к сервису. Зелёный означает доступный узел со всеми доступными привязанными сервисами. Жёлтый означает доступный узел с подтверждённым отказом хотя бы одного сервиса. Красный означает недоступный узел, в том числе выключенную ВМ. При недостатке свежих наблюдений узел серый. В карточке видны состояние самого узла, источник и время проверки, недоступные сервисы и сервисы без подтверждения. Для ВМ сетевой результат сопоставляется по MAC. Состояние Windows-служб остаётся диагностической информацией. Цвет сервисов определяется результатом функциональной проверки.

## Сбор снимка

Запускайте сборщик из корня установленного UI_VPN от учётной записи, которой доступны команды чтения netctl и файл Server Observer. Подготовьте каталог снимка с флагом setgid и группой, доступной сервису панели. Сборщик заменяет файл атомарно. При ошибке сборщика доступен предыдущий снимок, а наблюдения старше 25 минут отмечаются как устаревшие.

В файле привязок задаются устойчивые идентификаторы объектов из `network-context.yaml` и соответствие источникам. Значения ниже условные.

```json
{
  "roles": {
    "document_service": {"label": "Документооборот", "asset": "document-server"}
  },
  "guests": {
    "103": {"asset": "document-server", "mac": "02:00:00:00:00:03"}
  },
  "guest_probe_ips": {
    "103": "192.0.2.10"
  }
}
```

Перед добавлением привязки сопоставьте адрес цели проверки с гостевой ОС и запишите MAC её интерфейса из конфигурации Proxmox. При несовпадении MAC новая ВМ с таким же VMID отображается отдельным узлом. Коммутаторы читаются из netctl и сетевого контекста. Уверенность в соединениях определяется сведениями GitHub, netctl и LLDP.

`guest_probe_ips` задаёт IPv4-адреса ВМ для проверки ICMP из локального сегмента. Сборщик проверяет запущенную ВМ, активный интерфейс Proxmox и свежее соответствие IP и MAC из ARP роутера. После ответа ICMP он сверяет MAC с таблицей соседей сервера. Пропуск ответа оставляет эту проверку без подтверждения. Если Linux ограничивает ICMP непривилегированным процессам, для systemd-сборщика можно задать `AmbientCapabilities=CAP_NET_RAW` и `CapabilityBoundingSet=CAP_NET_RAW` в секции `[Service]`.

Для службы на госте, у которого пока нет идентификатора в сетевом инвентаре, добавьте запись в `guest_services` с ключом службы и полями `label`, `vmid` и `mac`. Сборщик связывает службу с ВМ по VMID и уникальному MAC из Proxmox. Проверки этой службы запускаются по адресу из `guest_probe_ips`, когда его подтверждает свежий ARP и сетевой интерфейс ВМ включён.

В этом же файле объект `service_probes` задаёт список проверок по ID сервиса. У каждого задания есть `type`, `ip` и `port`. Для HTTP или HTTPS укажите `path` и ожидаемый `body`, `body_contains` или `content_type`. Для DNS укажите абсолютное `name` и `record` (A, AAAA или SOA). Для LDAP укажите ожидаемый `naming_context` в ответе RootDSE. SMB2 проверяет согласование протокола. Список проверок может содержать до четырёх заданий, и зелёный статус требует подтверждения каждого. Сборщик также использует проверенные результаты готовности ACTI, здоровья Nextcloud и OnlyOffice и свежести резервной копии. Отсутствие функциональной проверки даёт серый статус.

Для службы, привязанной к серверу из сетевого контекста, задайте в `asset_services` запись по ID службы с полями `asset` и `label`. Адрес проверки должен совпадать с `management_ip` этого сервера. HTTPS по умолчанию проверяет системную цепочку доверия. Для сервера с самоподписанным сертификатом можно указать сверенный отпечаток `tls_sha256` из 64 шестнадцатеричных символов. При смене сертификата проверьте новый отпечаток перед обновлением привязки. Доступность веб-панели PBS и состояние резервных копий проверяются независимо.

Проверка `zabbix_api` вызывает `apiinfo.version` без учётных данных. В `path` укажите путь к `api_jsonrpc.php` конкретной установки. Результат показывает доступность API Zabbix.

Для автоматического чтения Proxmox используйте HTTPS-имя, соответствующее сертификату, и токен с разделением привилегий. Файл токена содержит значение заголовка `PVEAPIToken=USER@REALM!TOKENID=SECRET`. Сборщику нужны права чтения узлов, списка ВМ и конфигураций ВМ для сопоставления MAC. Укажите файл доверенного CA, если его нет в системном хранилище.

В `hypervisor_management_bridges` укажите мост управления для каждого проверяемого гипервизора по имени узла Proxmox. Карта подтверждает оба порта соединения, когда Proxmox показывает активный мост с одним активным Ethernet-интерфейсом, адрес моста совпадает с инвентарём, а свежий ARP и подтверждённая таблица MAC указывают на один порт коммутатора. Для мостов с несколькими интерфейсами или агрегацией карта сохраняет имеющиеся данные о портах.

Для портов сети ВМ карта уточняет имя интерфейса гипервизора по активному мосту Proxmox. Требуются один активный Ethernet-интерфейс в мосту и свежая запись MAC запущенной ВМ на уже подтверждённом порту коммутатора. При неоднозначном сопоставлении сохраняются данные инвентаря.

Для LACP укажите в списке `lacp_links` источник SNMP (`source`), имя агрегата (`aggregate`), имена его портов (`members`) и узел-партнёр из сетевого контекста (`asset`). Сборщик проверяет принадлежность каждого порта к агрегату, рабочее состояние LACP с обеих сторон и соответствие MAC партнёра свежему ARP его адреса управления. В карточке показываются подтверждённые порты коммутатора и номера портов партнёра из LACP. Эти номера не раскрывают имена интерфейсов в ОС партнёра.

Двустороннее LLDP подтверждает пару портов между коммутаторами, когда оба свежих объявления указывают друг на друга, MAC шасси однозначно сопоставляются со свежими ARP или SNMP, а на каждом порту наблюдается один сосед. Числовой псевдоним порта сопоставляется с `ifIndex` только при таком взаимном подтверждении.

Если таблица MAC показывает другое устройство за портом с подтверждённым соседом LLDP, карта сохраняет наблюдение о пути и снимает подтверждение этой пары портов. Двустороннее LLDP имеет приоритет при выборе соседа. Остальные подтверждённые порты той же связи остаются в карте.

```bash
python -m app.infrastructure_collect \
  --context /srv/network_configuration/config/network-context.yaml \
  --schema /srv/network_configuration/schemas/network-context.schema.json \
  --git-revision "$(git -C /srv/network_configuration rev-parse HEAD)" \
  --server-health /var/lib/openvpn-web/server-observer/latest.json \
  --bindings /etc/openvpn-web/infrastructure/bindings.json \
  --proxmox-url https://proxmox.example.invalid:8006 \
  --proxmox-token-file /etc/openvpn-web/infrastructure/pve-token \
  --proxmox-ca /etc/openvpn-web/infrastructure/pve-ca.pem \
  --output /var/lib/openvpn-web/infrastructure/latest.json
```

Сборщик можно вызывать из системного таймера каждые пять минут. По умолчанию панель читает файл из примера. Другой путь задаётся через `INFRASTRUCTURE_MAP_SNAPSHOT_PATH`. Для разового импорта используется `--proxmox-export` с полями `at`, `cluster`, `nodes`, `guests` и `configs`, где последнее поле содержит конфигурации привязанных ВМ по VMID. При запуске от учётной записи с прямым доступом к netctl задайте `NETCTL_USE_SUDO=0`.

## Просмотр в VR

Откройте карту через HTTPS в браузере гарнитуры. Кнопка «Открыть в VR» появляется, когда браузер подтверждает поддержку `immersive-vr`. Открывается текущая вкладка карты. Выбор узла контроллером показывает его имя и статус. Выйти можно штатным действием гарнитуры. [Спецификация WebXR](https://www.w3.org/TR/webxr/)
