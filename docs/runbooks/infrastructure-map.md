# Карта инфраструктуры

Раздел «Сеть и диагностика → Инфраструктура» читает готовый снимок. Веб, API `GET /api/v1/network/infrastructure` и инструмент MCP `openvpn_network_infrastructure` используют один формат. Для браузера действуют обычные права просмотра сети. Для API и MCP нужен токен с `network:read`.

Поля `status` и `mapStatus` возвращают итоговый цвет. `sourceStatus` содержит наиболее серьёзный статус среди свежих источников. Ответ сервиса и сбой обязательной проверки дают жёлтый цвет. Если Proxmox подтверждает остановку однозначно сопоставленной ВМ, её привязанные службы красные, а сетевые проверки этих служб пропускаются.

Через MCP передайте `query` с именем, псевдонимом, ID узла или номером ВМ, например `ВМ 103`. Поиск возвращает до 12 карточек с ID и цветом статуса, а также общее число совпадений и время снимка. Для проверок, соседей и сведений о портах вызовите инструмент ещё раз с `node_id`. Вызов без аргументов возвращает полный снимок.

Сводка `GET /api/v1/network/infrastructure?view=services` доступна в MCP через `{"view":"services"}`. Она возвращает `serviceAudit` с числом служб по итоговому цвету, идентификаторами узлов и зависимостей, источником и временем проверки доступности. Для каждой службы приводятся счётчики обязательных проверок и до шести обнаруженных отклонений, включая устаревшие результаты. Список содержит до 128 служб, проблемные идут первыми. Для всех подробностей откройте службу по `node_id`.

Для цепочки от службы или ВМ до коммутатора вызовите MCP с `{"view":"attachment","node_id":"role:directum"}` или API с `view=attachment&node_id=role%3Adirectum`. Ответ `attachment` показывает подтверждение размещения гостя, его адаптеры, мост, VLAN, интерфейсы хоста и наблюдения на коммутаторе. `guest_mac` означает наблюдение MAC гостя, `bridge_uplink` — наблюдение аплинка моста, `configured_bridge` — привязку по конфигурации. `physicalPair` появляется, когда свежая пара портов однозначно соответствует интерфейсу хоста из конфигурации моста и порту коммутатора из наблюдения. Записи `physicalPair` подтверждают физический сегмент пути. Функциональные проверки службы доступны в отдельной карточке.

Для сводки по всем ВМ вызовите MCP с `{"view":"attachment"}` или API с `view=attachment`. В `attachmentAudit` уровень `guest_mac_with_physical_pair` означает наблюдение MAC гостя и подтверждённую пару физических портов. `guest_mac` означает наблюдение MAC без пары портов, `bridge_with_physical_pair` — подтверждённую пару портов аплинка без наблюдения MAC гостя. Для остальных адаптеров указывается уровень `bridge_uplink`, `configured_bridge`, `unconfirmed` или `inactive`. Счётчики охватывают все ВМ снимка. Список `gaps` показывает до 64 ВМ с неполными данными, сначала работающие. Остановленные ВМ и явно отключённые адаптеры исключены из списка пробелов.

На веб-карте тот же сетевой путь находится в карточке ВМ или службы с единственной подтверждённой ВМ. Блок раскрывается сразу при наличии подтверждённой пары портов. Нажатие на порт открывает карточку интерфейса коммутатора. Блок обновляется вместе со снимком карты.

Для одного порта передайте вместе `node_id` и `port_name`, например `snr-s5210g-24tx` и `ge17`. Ответ включает состояние интерфейса, только относящиеся к нему связи и отдельные наблюдения о ВМ. Поле `basis` указывает, замечен ли MAC гостя (`guest_mac`) или известен путь через аплинк моста (`bridge_uplink`). Для выключенного гостя или отключённого адаптера наблюдение об аплинке содержит `configuredOnly: true`. Оно относится к настроенному мосту, а гостевой линк показан неактивным. В таком ответе подтверждение связи требует доказательства для выбранного порта.

У портов SNR с обнаруженным модулем карточка и поле `ports[].transceiver` показывают форм-фактор, производителя, известный тип среды, номинальную скорость модуля и время чтения SNMP. Сборщик сопоставляет индекс и имя интерфейса с текущим опросом. Через пять минут результат скрывается до следующего чтения. Скорость линка берётся из IF-MIB, а подтверждение удалённого порта требует отдельных данных.

Для поднятых портов с доступным EtherLike-MIB поле `ports[].linkMode` содержит текущий дуплекс. Для SNR сборщик также читает настройку автосогласования. Оба значения публикуются после сверки индекса и имени порта, а через пять минут без свежего чтения скрываются. Эти сведения также доступны в `pending[].portObservations` сводки топологии.

В веб-карте откройте «Интерфейсы» в карточке коммутатора и нажмите имя порта. Карточка покажет его состояние и относящиеся к нему записи о связях. Для переименованного порта с известным физическим номером веб-карта и MCP принимают текущее имя и псевдоним `PortN` из API. Запись из GitHub и наблюдение по MAC-таблице сохраняют собственные источники и статусы подтверждения. В разделе «Наблюдения о ВМ и контейнерах» можно открыть карточку гостя и увидеть гипервизор, мост, интерфейс, VLAN при наличии и время наблюдения. Запись о MAC гостя подтверждается таблицей коммутации. Запись об аплинке описывает путь через мост гипервизора. Ссылка сохраняет выбор в параметре `port`, а кнопка «Все порты» возвращает полный список.

Для выбранного порта с поднятым линком карта показывает средний приём и передачу, прирост ошибок и отброшенных пакетов за указанный интервал. API и MCP возвращают эти данные в `ports[].telemetry`. Интервал должен быть свежим, а счётчики и состояние порта должны относиться к одному сбору Network Observer.

В сводке `view=topology` поле `portCounterAudit` показывает число портов со свежими счётчиками `measuredPorts` и число портов с ненулевым приростом `affectedPorts`. В списке `ports` до 64 таких портов с именем узла, подписью порта при наличии и интервалом измерения. Список отсортирован по приросту ошибок, затем по отбросам. Измерение относится к указанному порту. Для установления причины и проверки дальнего конца нужны отдельные данные.

Если коммутатор отдал таблицу VLAN в том же сборе, карточка выбранного порта показывает PVID и VLAN с тегом и без тега. API и MCP публикуют данные в `ports[].vlanMemberships`. При разных ключах интерфейса и таблицы VLAN используется однозначный `ifIndex` внутри одного сбора.

Строка «VLAN по MAC-таблице» показывает номер VLAN и число уникальных MAC, изученных на поднятом порту в том же сборе. API и MCP публикуют агрегат `ports[].fdbVlans` без самих MAC. Этот источник подтверждает наблюдение в таблице коммутации. Для PVID и режима тегирования нужна таблица VLAN.

Строка «Изученных MAC» показывает число уникальных записей по всем VLAN, включая ноль. Она появляется, когда таблица MAC и состояние порта получены в одном успешном опросе FDB. API и MCP возвращают `fdbLearned` в `ports[]` и `portEvidence[].portStates`. Признак `partial` означает, что часть строк FDB была отброшена при разборе. Ноль записей сам по себе не подтверждает состояние дальнего конца линии.

На SNR значение `-31071` в Q-BRIDGE сопоставляется с `po1` при совпадении имени интерфейса, `ifIndex 100001` и привязки порта моста. Сопоставление сверено с BRIDGE-MIB для тех же записей. При агрегации MAC используется порт из того же SNMP-опроса.

В наблюдениях о связи отображаются состояния портов на обоих концах, где есть свежие данные. Для коммутаторов источником служит SNMP, для физических Ethernet-портов маршрутизаторов MikroTik — текущий опрос RouterOS. Карточка маршрутизатора показывает эти интерфейсы и время опроса. API и MCP указывают `source: "RouterOS"` в `ports[]` и в `portEvidence[].portStates`. Скорость отображается при наличии измерения. Имя `Slot0/N` сопоставляется с `PortN` при совпадении `ifIndex` с номером порта.

Для подтверждённого прямого соединения карта также сверяет пару портов, если оба показания свежие и получены с разницей до двух минут. В API и MCP результат виден в `portEvidence[].portComparison`. Сверка выявляет опущенный линк и различие двух известных скоростей. Для путей через промежуточные устройства показываются только отдельные наблюдения о портах.

Жёлтый штрих на линии отмечает свежий отказ порта или расхождение скоростей подтверждённой пары. При наличии показаний только о сбое на одном конце карточка указывает этот порт. Состояние узлов остаётся в их цветах. API возвращает такие пары в `links[].portAlerts`, а MCP в режиме `view=topology` показывает число и список в `topologyAudit.portAlertTotal` и `topologyAudit.portAlerts`.

Для включённых источников SNMP с профилем CSS326 сборщик читает корневой порт STP, MAC назначенного моста и двухбайтовый идентификатор его порта. Карточка показывает время опроса и открывает местный порт по нажатию. Наблюдение доступно в `nodes[].stpRootPath` и `topologyAudit.stpRootPaths` в течение пяти минут. Идентификатор относится к сегменту STP, поэтому по нему карта не добавляет физическую связь. [BRIDGE-MIB, RFC 4188](https://www.rfc-editor.org/rfc/rfc4188.html)

Показания Network Observer о корневом мосте доступны в `nodes[].stpRoot` и `topologyAudit.stpRoots`. Поле `localPort` указывает порт в сторону корня, `rootBridgeMac` содержит MAC корня, а `rootDeviceId` появляется при однозначном совпадении в инвентаре. Сборщик использует порт из того же опроса и скрывает результат через пять минут. Сведения STP сохраняют действующий статус физических пар.

Если назначенный мост опрашивается с профилем SNR, сборщик сопоставляет полные идентификаторы моста и порта с его собственной таблицей STP и актуальным интерфейсом. Однозначное совпадение возвращает `designatedPortName` и `designatedPortCheckedAt`. Карточка открывает этот интерфейс коммутатора. Путь по STP сохраняет отдельный статус от физической пары.

При совпадении корневого порта STP с портом взаимного наблюдения MAC карта показывает оба результата в карточке связи. Для однозначного MAC из инвентаря добавляется имя назначенного моста. API и MCP возвращают эти наблюдения в `portEvidence[].stpPaths` и `topologyAudit.pending[].observedPaths[].stpPaths`. Такая запись описывает путь STP. Пара физических портов сохраняет собственный статус подтверждения.

На D-Link и TP-Link сборщик читает состояние порта STP и параметр его включения через BRIDGE-MIB. Показания привязываются к свежему имени и ifIndex из IF-MIB. Карта показывает оба поля в деталях порта и связи отдельно от физического линка. В API и MCP результат доступен пять минут в `ports[].stpPort` и `topologyAudit.pending[].portObservations`. Подтверждение кабельной пары требует отдельного наблюдения соседства. [BRIDGE-MIB, RFC 4188](https://www.rfc-editor.org/rfc/rfc4188)

В карточке выбранного порта можно раскрыть до 16 объявлений LLDP из того же опроса, что и счётчики соседей. Список содержит заявленное имя и идентификаторы шасси и порта. Если MAC шасси закреплён ровно за одним другим устройством в GitHub, в объявлении появляется переход к этому узлу. API и MCP возвращают `lldpNeighbors` с `inventoryDeviceId` при совпадении и `lldpCheckedAt` в данных порта, а для открытых пар — `topologyAudit.pending[].lldpObservations` по сторонам связи. Идентификатор порта из LLDP может обозначать логический интерфейс, например `bond0`. Для подтверждения физической пары действуют отдельные правила.

Поле `portIdSubtype` содержит тип идентификатора из объявления LLDP. В открытой паре `missingPortSides` перечисляет стороны без имени порта, а `identifiedPeerSides` — стороны, с которых LLDP опознал противоположное устройство по MAC шасси.

На выбранном Ethernet-порту маршрутизатора список «Соседи RouterOS» показывает записи `/ip neighbor` из того же опроса, что и состояние порта. Запись относится к порту, когда RouterOS указывает ровно один известный Ethernet-интерфейс и его линк поднят. API и MCP возвращают до 16 наблюдений, их общее число и время опроса в `routerNeighbors`. Через десять минут показания скрываются. Запись из таблицы соседей показывает, где маршрутизатор видит устройство. Для подтверждения физической пары нужны дополнительные данные.

Для неподтверждённых связей сборщик дополнительно опрашивает до восьми известных портов на каждом коммутаторе после проверок подтверждённых пар. Сводка `topologyAudit.pending[].portObservations` показывает актуальное состояние, скорость и время измерения по каждой доступной стороне, в том числе когда вторая сторона ещё неизвестна. При наличии свежих данных в сводку входят трафик и счётчики ошибок (`telemetry`), число изученных MAC (`fdbLearned`) и параметры модуля (`transceiver`). У каждого замера есть своё время наблюдения. Сигнал линка подтверждает состояние порта. Подтверждение физической пары требует отдельных наблюдений.

В карточке связи раздел «Источники инвентаря» открывает датированные материалы из той ревизии сетевого контекста, по которой собран снимок. MCP показывает эти ссылки в `inventorySources` для записей из GitHub, включая `topologyAudit.pending` и `topologyAudit.inventoryPairs`. Дата `observedOn` относится к указанному документу. Время живого измерения остаётся в `at` или `checkedAt`.

`configuredLabel` показывает свежую подпись `ifAlias` из SNMP. В карточке выбранного порта и в деталях связи она отмечена как «Подпись на коммутаторе». Подпись доступна и для опущенного порта. Она отражает настройку устройства, а идентификация удалённого порта требует собственных наблюдений.

Для подтверждённой инвентарной пары с `vlans.tagged` или `vlans.untagged` карта сравнивает ожидаемый режим с измерениями каждого порта. Детали связи показывают режим выхода и отдельно изученные MAC в этой VLAN. Изученные MAC подтверждают наблюдение трафика в VLAN, а режим выхода подтверждается таблицей членства порта. Пустая или устаревшая таблица оставляет режим без подтверждения. В API данные доступны в `portEvidence[].vlanAudit`, а в MCP с `view=topology` — в `topologyAudit.vlanAudits`.

Если TP-Link T1600G возвращает пустые стандартные таблицы VLAN и PVID, Netctl читает фирменные списки тегированных и нетегированных портов и PVID. Номера портов сопоставляются с ifIndex по профилю TP-Link. Неполные или противоречивые списки помечаются как ошибка опроса. [MIB для T1600G-52TS](https://www.tp-link.com/us/support/download/t1600g-52ts/)

Для известных портов с обеих сторон карта указывает, подтверждена ли пара свежим наблюдением (`pairEvidence: "current"`) или подтверждённой записью GitHub (`"verified_inventory"`). Одностороннее наблюдение не получает признака подтверждённой пары. При сверке двусторонних MAC-таблиц имена портов и подтверждённые псевдонимы из текущего опроса сопоставляются с инвентарём.

Связь с `vlan.mode: tagged_transit` отображается как транзитный сегмент и исключается из подсчёта физических пар. В `local_vlan_transits` можно указать ID подтверждённой связи и ID локального узла. Сборщик проверяет интерфейс, номер VLAN, адрес с префиксом и прямой маршрут к соседу. ICMP использует локальный адрес и интерфейс, а результат и задержка видны в карточке транзита и MCP.

Параметр `local_vlan_peer_adapters` задаёт по ID транзита адаптер соседа из текущей конфигурации Proxmox, например `net2`. После успешного ICMP сборщик сверяет MAC этого адаптера со свежим соседством Linux на ожидаемом VLAN. Совпадение отображается в карточках ВМ и транзита. В сводке `attachmentAudit` оно даёт уровень `local_neighbor` или `local_neighbor_with_physical_pair`, если есть отдельное подтверждение физической пары аплинка. Наблюдение MAC на коммутаторе учитывается отдельно.

`wireguard_policy_checks` задаёт список ID проверок из `routing_intent`, привязанных к локальному VLAN-транзиту. Установите `deploy/openvpn-policy-report.py` в `/usr/local/libexec/openvpn-policy-report` с владельцем root и подключите `openvpn-policy-observer.service` через `Wants` и `After` в службе сборщика. Отчёт содержит подтверждённую маркировку на входе и время последнего handshake без ключей. Сборщик проверяет выбор таблицы и интерфейса локальным запросом маршрута для адреса из диапазона документации. Запрос маршрута не отправляет пакеты. При недостатке свежих данных о handshake результат остаётся без подтверждения. API и MCP возвращают наблюдения в `serviceChecks[].wireguardPolicy`.

Карточка гипервизора показывает физические интерфейсы, существование которых подтверждает Proxmox API. В `ports[]` и в наблюдениях о связи поле `proxmoxActive` отражает, отмечен ли интерфейс активным в ОС. Источник `Proxmox · sysfs` дополнительно показывает фактический линк и согласованную скорость.

Для опроса sysfs установите `deploy/proxmox-port-observer.py` в `/usr/local/libexec/ui-vpn-port-observer` с владельцем root. Учётная запись `ui-vpn-ports` работает без групп администрирования и с заблокированным паролем. Для отдельного ключа задайте в `authorized_keys` параметры `restrict,from="<IP сборщика>",command="/usr/bin/python3 -I /usr/local/libexec/ui-vpn-port-observer"`. Публичные ключи SSH-серверов Proxmox сверяются через уже доверенный доступ и закрепляются за их каноническими адресами.

Сервис `openvpn-infrastructure.service` получает ключ и файл известных хостов через `LoadCredential` с именами `pve-port-ssh-key` и `pve-port-known-hosts`. Параметр `proxmox_port_observer: true` в привязках включает опрос онлайн-узлов по их IPv4 из сетевого контекста. Сборщик сверяет имя узла и обновляет только интерфейсы из Proxmox API. При недоступном SSH или отсутствующих показаниях карта продолжает показывать данные API для этих портов.

Для поднятого физического порта, напрямую входящего в мост с фильтрацией 802.1Q, тот же экспортёр читает `bridge vlan show`. Карта использует членство VLAN для сверки подтверждённых связей из сетевого контекста. Мосты с выключенной фильтрацией и интерфейсы под агрегатами не дают такого подтверждения. На узлах со старым экспортёром продолжают обновляться линк и скорость.

В том же цикле сборщик опрашивает по SNMP порты из подтверждённых пар GitHub, если обе стороны доступны по SNMP или одна из них уже опрошена через sysfs Proxmox. Адрес источника сверяется с каноническим адресом коммутатора, а `ifName` подтверждает соответствие имени порта текущему `ifIndex`. Проверка линка действует пять минут. Время опроса VLAN, MAC-таблицы и счётчиков сохраняется отдельно.

При выборе физического порта гипервизора список наблюдений включает ВМ и контейнеры на мостах, в конфигурации которых указан этот интерфейс. MCP возвращает такие записи как `guestObservations[].basis = "host_bridge_member"` с состоянием моста и признаком отключённого гостевого адаптера. Запись описывает состав моста на момент опроса. Фактический сетевой трафик гостя требует отдельного наблюдения.

Общая карта включает все узлы снимка, в том числе ВМ и контейнеры без привязки к сервису. Зелёный означает доступный узел со всеми доступными привязанными сервисами. Жёлтый означает доступный узел с подтверждённым отказом сервиса или сбоем обязательной проверки. Красный означает недоступный узел, в том числе выключенную ВМ. При недостатке свежих наблюдений узел серый. В карточке видны состояние самого узла, источник и время проверки, недоступные сервисы, сервисы со сбоями проверок и сервисы без подтверждения. API и MCP возвращают эти списки в `serviceAvailability.unavailable`, `serviceAvailability.degraded` и `serviceAvailability.unknown`. Для ВМ сетевой результат сопоставляется по MAC. Доступность сервиса определяется функциональной проверкой. Состояние Windows-служб влияет на цвет только для проверок, явно отмеченных обязательными.

## Сбор снимка

Запускайте сборщик из корня установленного UI_VPN от учётной записи, которой доступны команды чтения netctl и файл Server Observer. Подготовьте каталог снимка с флагом setgid и группой, доступной сервису панели. Сборщик заменяет файл атомарно. При ошибке сборщика доступен предыдущий снимок. Обязательные проверки сервисов из UI_VPN устаревают через 5 минут, Server Observer через 15 минут, остальные наблюдения по умолчанию через 25 минут.

При отказе основного опроса Proxmox сборщик публикует свежие наблюдения из остальных доступных источников. API и MCP указывают `collectionIssues: ["proxmox"]`, а веб-карта показывает сообщение о неполном снимке. Если сетевой контекст совпадает, из последнего снимка сохраняются имена и VMID известных гостей, узлы кластера и прежние связи размещения с признаком «без подтверждения». Состояния ВМ, интерфейсы и другие показания Proxmox появляются снова после успешного опроса.

При ошибке чтения Network Observer снимок продолжает обновляться по Proxmox, Server Observer и независимым проверкам сервисов. API и MCP добавляют `network_observer` в `collectionIssues`. Веб-карта предупреждает об отсутствии свежих данных SNMP, LLDP и MAC-таблиц. Связи и устройства из сетевого контекста остаются на карте.

Для показаний Server Observer карта применяет срок свежести самого источника в 15 минут. API и MCP сообщают `server_observer_stale` для устаревшего отчёта и `server_observer_unavailable` при его отсутствии, недоступности или ошибке сбора. Независимые проверки сервисов продолжаются.

В файле привязок задаются устойчивые идентификаторы объектов из `network-context.yaml` и соответствие источникам. Значения ниже условные.

```json
{
  "roles": {
    "document_service": {"label": "Документооборот", "asset": "document-server"}
  },
  "guests": {
    "103": {"asset": "document-server", "mac": "02:00:00:00:00:03"}
  },
  "guest_probe_ips": {
    "103": "192.0.2.10"
  }
}
```

Перед добавлением привязки сопоставьте адрес цели проверки с гостевой ОС и запишите MAC её интерфейса из конфигурации Proxmox. При несовпадении MAC новая ВМ с таким же VMID отображается отдельным узлом. Коммутаторы читаются из netctl и сетевого контекста. Уверенность в соединениях определяется сведениями GitHub, netctl и LLDP.

`guest_probe_ips` задаёт IPv4-адреса ВМ для проверки ICMP из локального сегмента. Сборщик проверяет запущенную ВМ, активный интерфейс Proxmox и свежее соответствие IP и MAC из ARP роутера. После ответа ICMP он сверяет MAC с таблицей соседей сервера. Пропуск ответа оставляет эту проверку без подтверждения. Если Linux ограничивает ICMP непривилегированным процессам, для systemd-сборщика можно задать `AmbientCapabilities=CAP_NET_RAW` и `CapabilityBoundingSet=CAP_NET_RAW` в секции `[Service]`.

Параметр `guest_auto_arp_probes: true` добавляет до 48 проверок за цикл для запущенных ВМ без явного `guest_probe_ips`. Адрес берётся из свежего ARP только при единственной паре IPv4 и MAC для включённых интерфейсов ВМ. ICMP выполняется при прямом маршруте с сервера UI_VPN. Карта выбирает более свежий положительный результат Netctl или проверку с подтверждением MAC. Адреса и правила проверок гостевых сервисов по-прежнему задаются явной привязкой.

Для ВМ, которую локальный трафик редко выводит на физический коммутатор, в `guest_attachment_fdb` можно задать имя SNMP-источника SNR по VMID. Для той же ВМ задайте `guest_probe_ips` и `guest_router_arp_sources`. После сверки MAC с Proxmox и свежим ARP сборщик отправляет один ARP-запрос с указанного маршрутизатора и читает изученную запись BRIDGE-MIB на SNR. Имя и рабочее состояние порта проверяются в IF-MIB. Дополнительное наблюдение относится к MAC и порту, VLAN берётся из обычного опроса.

После успешного чтения конфигурации гостя карточка показывает число заданных адаптеров Proxmox и состояние адаптеров с распознанным мостом. API и MCP возвращают эти показания в `guestNetwork` с временем опроса. У запущенного гостя без заданных адаптеров и без сетевых наблюдений карта оставляет доступность неподтверждённой и показывает причину из Proxmox.

Для службы на госте, у которого пока нет идентификатора в сетевом инвентаре, добавьте запись в `guest_services` с ключом службы и полями `label`, `vmid` и `mac`. Сборщик связывает службу с ВМ по VMID и уникальному MAC из Proxmox. Проверки этой службы запускаются по адресу из `guest_probe_ips`, когда его подтверждает свежий ARP и сетевой интерфейс ВМ включён.

Если адрес для проверки ещё не подтверждён или расходится с настройкой, карта показывает «Не запущена» и причину. API и MCP возвращают `serviceChecks[].skipped: true` и время, когда сборщик проверил условие запуска. Сетевой запрос не выполняется, а адрес цели не публикуется в этой записи.

Для службы, уже проверяемой Server Observer, укажите `vmid` и `mac` в соответствующей записи `roles` без поля `asset`. Перед настройкой сверьте адрес цели Server Observer с MAC сетевого интерфейса ВМ. Карта привязывает существующую карточку службы к ВМ при совпадении VMID и уникального MAC из свежей конфигурации Proxmox. Результаты Server Observer остаются в этой карточке.

В списке `used_by` записи `roles` или `guest_services` можно указать ID сервисов, для которых зависимость уже проверена. Например, `roles.acti_backup.used_by: ["role:acti"]` связывает проверку копии на FILESERVER с ACTI. Явно заданная зависимость от службы гостя остаётся видна при пропаже данных Proxmox. Размещение и запуск проверки требуют свежих данных о ВМ, уникального MAC и совпадения адреса с ARP.

Для дополнительной проверки ВМ по ARP укажите в `guest_router_arp_sources` имя включённого источника MikroTik API по VMID. При отсутствии ответа на локальный ICMP сборщик использует интерфейс роутера из свежей записи ARP и принимает ответ только от MAC интерфейса ВМ из Proxmox.

Для проверки физического устройства по MAC укажите в `asset_mac_probes` запись по ID устройства с полями `source`, `interface` и `mac`. MAC должен принадлежать только этому устройству в сетевом инвентаре. Успешный ответ отображается как `MAC ping · L2` с источником и временем. При отсутствии IP-проверки ответ подтверждает доступность на канальном уровне. Адрес управления, состояние сервисов и порты подключения требуют собственных наблюдений.

Для физического узла можно указать адрес из сетевого контекста в `asset_ip_checks`. Сборщик запускает ICMP после сопоставления MAC устройства с подтверждённым портом. Ответ подтверждает доступность IP-адреса. Принадлежность IP узлу требует отдельного наблюдения. Для свежей записи MAC-таблицы карта и API показывают состояние порта коммутатора, даже когда порт на стороне узла неизвестен.

Для коммутатора, обнаруженного по LLDP, адрес в `asset_ip_checks` проверяется при однозначном соседстве и совпадении MAC шасси с инвентарём, свежей записью хоста и ARP. Ответ используется как положительное наблюдение об устройстве. Карточка, API и MCP показывают способ `ICMP · LLDP + ARP` и время сверки адреса `identityCheckedAt`. Отсутствие ответа оставляет доступность на основе других наблюдений.

При выборе порта карта показывает число обнаруженных LLDP-соседей. Та же строка доступна в карточке связи для каждой стороны с подходящим наблюдением. API и MCP возвращают `lldpNeighborCount` в `ports[]` и в `portEvidence[].portStates`. Учитываются уникальные пары идентификаторов устройства и порта из того же опроса, что и состояние активного локального порта. Отсутствие поля означает, что наблюдений для этого опроса нет. Число соседей само по себе не подтверждает прямое соединение.

В этом же файле объект `service_probes` задаёт список проверок по ID сервиса. У каждого задания есть `type`, `ip` и `port`. Для HTTP или HTTPS укажите `path` и ожидаемый `body`, `body_contains` или `content_type`. Для DNS укажите абсолютное `name` и `record` (A, AAAA или SOA). DNS-проверка сопоставляет ответ с запрошенным именем, включая цепочку CNAME. Для записей A и AAAA можно задать `expected_addresses`. Сборщик проверит совпадение полного набора адресов. Для LDAP укажите ожидаемый `naming_context` в ответе RootDSE. SMB2 проверяет согласование протокола. Список проверок может содержать до четырёх заданий, и зелёный статус требует подтверждения каждого. Сборщик также использует проверенные результаты готовности ACTI, здоровья Nextcloud и OnlyOffice и свежести резервной копии. Отсутствие функциональной проверки даёт серый статус.

Свежий ответ хотя бы одной основной проверки устанавливает доступность сервиса. Сбой другой обязательной проверки даёт жёлтый статус. Красный требует свежего подтверждённого отказа по всем основным проверкам. UI, API и MCP учитывают время каждого результата при чтении снимка. Тайм-аут оставляет проверку без подтверждения. Зелёный требует свежего успешного результата каждой обязательной проверки. Параметр `component: true` оставляет проверку обязательной, но исключает её из определения доступности всего сервиса. Для Directum основной считается `/Client/api/profile.public-server-info`. Отметьте `/Client/`, `/Integration/health` и DNS как обязательные компоненты. Клиентский API должен вернуть JSON с `ProductName: Directum RX` и выключенным режимом обслуживания. При подтверждённом отказе клиентского API статус Directum красный, даже если интеграция отвечает. Для консоли хранилища отметьте так `/` и используйте `/ready` как основную проверку. API и MCP возвращают признаки `serviceChecks[].required` и `serviceChecks[].component`. Наблюдения маршрутов из `route_evidence` считаются обязательными компонентами и требуют отдельной проверки доступности сервиса.

Для HTTP параметр `http_host` задаёт имя в заголовке Host. Соединение устанавливается с настроенным `ip`. Имя видно в карточке и в `serviceChecks[].httpHost`. Для Directum используйте имя клиента во всех трёх HTTP-проверках и добавьте обязательную DNS-проверку с `component: true` через внутренний резолвер. Набор `expected_addresses` должен содержать IP из HTTP-проверок. DNS-проверка использует то же имя, записанное в абсолютной форме с точкой в конце.

Для клиентского API Directum задайте `json_fields` как `{"ProductName":"Directum RX","PlatformName":"Sungero","MaintenanceModeState.IsEnabled":false,"MaintenanceModeState.IsSafeModeEnabled":false}` и `json_unavailable` как `{"ProductName":"Directum RX","PlatformName":"Sungero","MaintenanceModeState.IsEnabled":true}`.

Для службы, привязанной к серверу из сетевого контекста, задайте в `asset_services` запись по ID службы с полями `asset` и `label`. Адрес проверки должен совпадать с `management_ip` этого сервера. HTTPS по умолчанию проверяет системную цепочку доверия. Для сервера с самоподписанным сертификатом можно указать сверенный отпечаток `tls_sha256` из 64 шестнадцатеричных символов. При смене сертификата проверьте новый отпечаток перед обновлением привязки. Доступность веб-панели PBS и состояние резервных копий проверяются независимо.

Для HTTP-страницы, которую устройство отдаёт в gzip, установите `allow_gzip: true` и укажите ожидаемый признак страницы. Сборщик ограничивает сжатое и распакованное тело до 32 КиБ и проверяет признак после распаковки. Проверка SwOS читает `/index.html` и сверяет заголовок страницы. Для проверки входа в панель нужны отдельные данные.

Для FTP используйте `type: ftp_features` на настроенном порту. Сборщик ожидает приветствие `220`, затем отправляет `FEAT` и сверяет полный ответ `211` с ограничением времени и размера. Код `421` означает недоступность управляющего соединения, неожиданный код оставляет результат без подтверждения. Карта и API публикуют числовой `ftpReply`. Эта проверка работает без входа и открытия канала данных. [RFC 959](https://www.rfc-editor.org/info/rfc959/) · [RFC 2389](https://www.rfc-editor.org/info/rfc2389/)

Для проверки срока действия известного сертификата на TLS-порту используйте `type: tls_certificate` и проверенный отпечаток `tls_sha256`. Сборщик сверяет отпечаток конечного сертификата и даты его действия. При смене отпечатка результат остаётся без подтверждения до сверки нового сертификата. Карта и MCP показывают дату окончания срока и согласованную версию TLS. Проверка заканчивается на TLS-рукопожатии.

Для проверки службы на адресе шлюза сегмента укажите `gateway_segment` в записи `asset_services`. Сборщик использует `gateway` этого сегмента, когда `gateway_device` совпадает с `asset`. Для DNS можно явно выбрать `transport: udp` или `transport: tcp`. Без этого параметра используется UDP с переходом на TCP при усечённом ответе. При явном `transport: udp` сборщик ждёт ответ с адреса и порта назначения. Если до тайм-аута пришёл только ответ с совпадающим запросом от другого адреса или порта, проверка фиксирует отказ `dns_unexpected_source` и публикует `dns.unexpectedResponder`. Содержимое такого ответа отбрасывается. Отсутствие ответа оставляет статус неподтверждённым. [Документация dnspython](https://dnspython.readthedocs.io/en/latest/query.html) · [RFC 5452](https://www.rfc-editor.org/rfc/rfc5452)

Для DNS через известный IPv4-маршрут укажите `route_via` с ожидаемым следующим шлюзом. Сборщик сверяет маршрут UI_VPN и отправляет запрос с найденного исходного адреса только при совпадении шлюза. Карточка и MCP показывают этот адрес, интерфейс и шлюз в `localRoute`. Для результата из самого сегмента выполните отдельный замер на подключённом к нему устройстве.

`proxmox_backup_monitor` добавляет к PBS проверку заданий Proxmox. Укажите `asset`, ID хранилища Proxmox в `storage` и пороги в часах для VMID в `max_age_hours`, например `{"asset":"pbs","storage":"pbs","max_age_hours":{"102":30}}`. Сборщик сверяет активное расписание, хранилище и итог по каждой ВМ в завершённых заданиях `vzdump`. Неполный журнал или отсутствие результата оставляет проверку без подтверждения. В API и MCP доступны `backupVmid`, `backupCompletedAt` и `backupMaxAgeHours`. Проверка подтверждает результат задания в Proxmox. Проверка целостности и восстановление выполняются отдельно.

Карточки ВМ и контейнеров показывают состояние активного расписания для указанного хранилища в `backupCoverage`. Результат копирования относится к конкретному VMID и влияет на цвет этой ВМ при настроенном пороге. Из карточки можно перейти к общей проверке на PBS и обратно. Отсутствие в расписании относится только к указанному хранилищу и оставляет доступность гостя на основе его собственных проверок.

Для HTTP-проверок с JSON-ответом задайте `json_fields` с ожидаемыми строковыми или логическими значениями. Для вложенных полей укажите путь через точку. Поле `json_unavailable` может описывать явный отказ, например включённый режим обслуживания. По умолчанию проверяется тип `application/json`. Остальные поля могут меняться, например номер версии. Этот режим используется отдельно от `body` и `body_contains`. Некорректный список заданий отображается как неподтверждённая обязательная проверка сервиса.

Для HTTP и HTTPS карта, API и MCP показывают фактический код ответа `serviceChecks[].httpStatus` и причину сбоя `reason`, когда она известна. При ошибке TLS или TCP до ответа код отсутствует. Сборщик не публикует тело ответа, заголовки и адрес назначения перенаправления.

Проверки `icmp` из UI_VPN показывают задержку Echo Reply в `serviceChecks[].roundTripMs`. Отсутствие ответа, сообщение о недостижимости и ошибка выполнения ping оставляют результат без подтверждения и видны как разные причины. Если при недостижимости известен отправитель, карта показывает его адрес. Проверки с `supplemental: true` обозначены как дополнительные и не определяют доступность сервиса.

Карточка DNS-проверки показывает имя и тип записи, код ответа, транспорт и до 16 фактических адресов A или AAAA. API и MCP возвращают эти сведения в `serviceChecks[].dns`. Отдельно отмечаются отсутствие записи требуемого типа и несовпадение с ожидаемым набором адресов.

Если API сообщает об отказе в JSON-ответе с HTTP 200, задайте `json_unavailable` вместе с `json_fields`. Совпадение всех полей `json_unavailable` означает недоступность и имеет приоритет над полями успешного ответа. Например, SonarQube сообщает `status: DOWN` в `/api/system/status`.

Для HTTPS с внутренним CA укажите абсолютный путь `tls_ca_file`. Параметр `tls_server_name` задаёт имя для проверки сертификата и заголовка Host, а TCP-соединение по-прежнему открывается к проверенному `ip`. Эти параметры используются отдельно от `tls_sha256`. Обновлённый сертификат проходит проверку, если его имя совпадает и цепочка ведёт к доверенному CA.

Проверка `smb` сверяет ответ SMB2 NEGOTIATE с отправленным запросом. Карта, API и MCP показывают целевой адрес, согласованный диалект `smbDialect` и требование подписи `smbSigningRequired`. Сборщик предлагает SMB 2.0.2, 2.1, 3.0 и 3.0.2. Проверка заканчивается до входа и открытия общей папки.

Для IPMI LAN добавьте отдельную службу контроллера в `asset_services` с `require_network_identity: true` и пробу `ipmi_lan` на UDP/623. Сборщик подтверждает адрес по ARP и FDB, затем ожидает ответ RMCP Presence Pong с тем же идентификатором запроса и признаком поддержки IPMI. Тайм-аут оставляет состояние без подтверждения. Ответ подтверждает доступность IPMI LAN с UI_VPN. Вход в систему, питание сервера и физический порт контроллера проверяются отдельно.

Проверка `rtsp_options` отправляет один RTSP OPTIONS на явно заданные `ip`, `port` и `path`. Сборщик сверяет CSeq и публикует код в `serviceChecks[].rtspStatus`. Код 401 с корректным запросом авторизации подтверждает работу RTSP на заданном ресурсе. Проверка заканчивается после заголовка ответа. Доступность видеопотока требует отдельной проверки.

Проверка `ssh_identification` открывает TCP-соединение на заданные `ip` и `port` и читает до 1024 байт. Сборщик подтверждает доступность по строке идентификации SSH 2.0 или совместимой 1.99, затем закрывает соединение. Для совместимости с ViPNet допускается завершение строки одиночным LF. Обмен ключами и вход в систему не выполняются. Текст ответа и версия серверного ПО не публикуются. [RFC 4253](https://www.rfc-editor.org/rfc/rfc4253.html#section-4.2)

Проверка `smb_mount` читает метаданные корневого каталога уже подключённого CIFS/SMB3-ресурса. Укажите `ip`, имя ресурса `share`, локальную точку `mount` и `component: true`. Перед чтением и после него сборщик сверяет источник и идентификатор подключения. Ожидающее автоподключение даёт «Нет подтверждения». API и MCP публикуют адрес ресурса в `smbShare`. Содержимое каталога и параметры аутентификации не публикуются.

Проверка `zabbix_api` вызывает `apiinfo.version` без учётных данных. В `path` укажите путь к `api_jsonrpc.php` конкретной установки. Результат показывает доступность API Zabbix.

Проверка `postgresql` отправляет PostgreSQL SSLRequest. При ответе `S` сборщик выполняет TLS-рукопожатие и показывает согласованную версию в `serviceChecks[].tlsVersion`. При ответе `N` протокол отвечает, а сервер отклонил TLS. Ошибка рукопожатия оставляет доступность без подтверждения. API и MCP возвращают результат согласования в `postgresqlTls`. Проверка заканчивается до StartupMessage, не проверяет подлинность сертификата и не выполняет SQL-запросы.

Для резервирования ACTI результат проверки свежести копии учитывается только при свежем и валидном отчёте watchdog. Карточка показывает количество снимков и возраст последнего снимка с пределом 30 часов, если его дата подтверждена. Если отчёт просрочен или не прошёл проверку, копия и ёмкость хранилища остаются без подтверждения.

Для цели `directum` в конфигурации Server Observer можно указать `listener_ports` с фактическими TCP-портами компонентов `mongo`, `rabbitmq` и `redis`. Проверка внутри ВМ сопоставляет порт в состоянии Listen с процессом-владельцем. В карточке Directum эти результаты видны отдельно от состояния служб Windows и веб-проверок.

Для самостоятельных карточек зависимостей настройте `guest_services` по VMID и MAC гостя, добавьте адрес в `guest_probe_ips` и укажите `used_by: ["role:directum"]`. Проверка `mongodb_ping` ожидает успешный ответ `ping` от самостоятельного экземпляра MongoDB. `amqp_start` ожидает кадр `Connection.Start` от RabbitMQ и завершает соединение до авторизации. `redis_ping` ожидает `PONG`. При тайм-ауте или несовпадении ответа статус остаётся неподтверждённым. [MongoDB](https://www.mongodb.com/docs/manual/reference/command/ping/) · [RabbitMQ](https://www.rabbitmq.com/resources/specs/amqp0-9-1.pdf) · [Redis](https://redis.io/docs/latest/commands/ping/)

Для проверки маршрута от ВМ Directum до PostgreSQL задайте `postgresql_endpoint` с IP и TCP-портом базы в цели `directum`. Добавьте `postgresql_from_directum` в `roles.directum.required_observer_checks` карты. Server Observer отправляет PostgreSQL SSLRequest из Windows и считает ответ `S` или `N` подтверждением протокола. Явный отказ соединения означает сбой обязательной проверки. Тайм-аут или неожиданный ответ оставляют её неподтверждённой. Проверка завершается до TLS-рукопожатия, входа и SQL-запросов. [Документация PostgreSQL](https://www.postgresql.org/docs/current/protocol-flow.html)

В записи `roles` файла привязок список `required_observer_checks` задаёт имена обязательных проверок Server Observer для сервиса. При работающем веб-интерфейсе подтверждённый сбой обязательной проверки или подтверждённой зависимости даёт жёлтый статус сервиса и доступной ВМ. Отсутствующий или устаревший обязательный результат оставляет статус без подтверждения, если известных сбоев нет. Проверки ресурсов отображаются в карточке и учитываются в цвете только при явном включении в этот список.

Функциональные проверки Server Observer, по которым карта определяет доступность ACTI, Nextcloud, ONLYOFFICE и резервного копирования ACTI, всегда входят в обязательные. Для резервного копирования ACTI обязательны свежесть копии и ёмкость её хранилища. Без актуального отчёта watchdog оба результата остаются неподтверждёнными. Повторяющиеся записи одного обязательного результата учитываются как одна неподтверждённая проверка.

Для запущенных ВМ и контейнеров с однозначным VMID поле `nodes[].resources` показывает CPU, vCPU, использованную и выделенную память и время работы по Proxmox. `checkedAt` фиксирует время чтения списка гостей. Карточка службы показывает те же ресурсы и ссылку на ВМ, когда у неё одна подтверждённая привязка к гостю. Память отражает метрику Proxmox. Данные о свободном месте внутри гостевой ОС поступают от отдельных проверок.

Поле `nodes[].guestIo` содержит средние скорости сети и диска в байтах в секунду, время последнего чтения и длительность интервала. Сборщик сравнивает соседние снимки Proxmox для одного гостя на одном хосте. Интервал должен быть от 30 до 300 секунд, а время работы гостя должно увеличиваться согласованно с длительностью интервала. При уменьшении накопительного счётчика скрывается соответствующая пара скоростей. После миграции, перезапуска или пропуска опроса нужен новый сопоставимый интервал. Веб показывает скорости в разделе ресурсов ВМ.

Для свободного места на дисках и размера журналов Directum карточка показывает измерение, порог предупреждения и время отчёта Server Observer. Раздел проверок раскрывается при свежем предупреждении или критическом значении. API и MCP возвращают исходные значения в `observed` и `warningThreshold` с единицей `unit`.

Server Observer измеряет доступную физическую память Windows у Directum, файлового сервера и Active Directory через `Win32_OperatingSystem`. `windows_memory_available_bytes` показывает объём в байтах, `windows_memory_available_percent` — долю от видимой Windows физической памяти. Для Nextcloud и OnlyOffice поля `linux_memory_available_bytes` и `linux_memory_available_percent` строятся из `MemAvailable` и `MemTotal` в `/proc/meminfo`. Карта показывает эти измерения без порога тревоги. При недоступном источнике памяти остальные проверки службы сохраняются.

Проверка `sip_options` показывает доступность SIP по UDP с точки сбора UI_VPN. Сборщик сопоставляет верхний Via branch, Call-ID и CSeq с отправленным запросом. Он пропускает посторонние пакеты и ждёт финальный ответ после промежуточного кода 1xx. Всего до трёх отправок одного запроса с окнами ожидания 0,5, 1 и 1,5 секунды. ICMP Port Unreachable с адреса назначения и финальные SIP-коды 500, 502, 503 и 504 дают статус недоступности. Тайм-аут, только промежуточный ответ и отказ с другого или неизвестного адреса оставляют доступность без подтверждения. Карточка и API показывают число попыток, причину, адрес отправителя ICMP и числовой код SIP для ответа, соответствующего запросу. Доступность веб-панели АТС проверяется отдельно.

Параметр `route_via` в проверке SIP сверяет IPv4-шлюз и привязывает сокет к адресу, выбранному ОС для маршрута. Карточка и MCP показывают адрес источника, интерфейс и шлюз. Если маршрут не подтверждён, проверка оставляет доступность без подтверждения и пропускает запрос.

Проверка `openvpn_management` читает состояние демона и число клиентских сессий из локального сокета. Связность подтверждается, когда демон сообщает `CONNECTED` и есть хотя бы одна сессия. При полном ответе без клиентов карта показывает ноль и оставляет связность без подтверждения. Настроенный UDP-порт публикуется как `configuredPort`. Для проверки нового подключения извне нужна отдельная клиентская проверка.

Проверка `openvpn_tunnel` читает состояние интерфейса Linux на сервере UI_VPN. В задании укажите `interface`, ожидаемый IPv4-адрес с префиксом в `address` и `component: true`. Проверка подтверждает тип TUN, флаги `UP` и `LOWER_UP` и точное совпадение адреса и префикса. Интерфейс и адрес доступны в карточке, API и MCP как `tunnelInterface` и `tunnelAddress`.

В `ipsec_links` укажите идентификатор `policy_based_ipsec` из сетевого контекста и поля `label`, `local_source`, `remote_source`, `remote_segment`. Сборщик читает политики с обоих маршрутизаторов и проверяет фазу 2 для каждой пары сетей и ожидаемых IPsec-партнёров. Ошибка чтения оставляет соответствующее направление без подтверждения. Проверки передачи данных и доступности приложений выполняются отдельно.

Параметр `connectivity` в этой же привязке включает отдельную проверку ICMP в обоих направлениях. Укажите `asset` сервера UI_VPN и `label` проверки. Адреса берутся из сетевого контекста и должны входить в сети политик IPsec. Удалённый MikroTik с SSH выполняет один запрос с адреса управления через действующую учётную запись источника. Проверка показывает связность двух адресов.

Запись `route_evidence` связывает ID сервиса с маршрутом из `routing_intent` и источником Network Observer. Необязательный список `host_routes` добавляет до четырёх точных маршрутов `/32` или `/128` внутри объявленных сетей. Карта показывает до 12 маршрутов, включая основные префиксы. Для каждого префикса карта показывает совпадение шлюза, свежую запись о неактивном маршруте, однозначно наблюдаемый другой шлюз или маршрут, отбрасывающий трафик. Несколько активных шлюзов оставляют результат без подтверждения. Время относится к наблюдению маршрутизатора. Доступность прикладного сервиса за шлюзом проверяется отдельно.

Параметр `route_via` в IPv4-проверке `icmp` задаёт ожидаемый первый шлюз UI_VPN. Сборщик читает выбранные ядром исходный адрес, интерфейс и шлюз. ICMP отправляется при совпадении шлюза. Карта, API и MCP показывают этот маршрут отдельно от ответа ICMP в `serviceChecks[].localRoute`.

В `transit_links` укажите идентификатор транзитного сегмента из сетевого контекста и поля `asset`, `source`, `peer` и `label`. Для пары IPv4-адресов в /30 или /31 карта подтверждает порт MikroTik по активному подключённому маршруту, рабочему Ethernet-интерфейсу и свежему ARP партнёра на этом же интерфейсе. Сборщик проверяет адрес партнёра по ICMP. Доступность приложений за ним проверяется отдельно.

Для WAN с `gateway: pppoe_peer` сборщик читает имя сессии, её родительский интерфейс и два флага состояния через настроенный SSH-источник RouterOS. Карта показывает состояние сессии и логическую привязку к интерфейсу. API и MCP возвращают подробности в `serviceChecks[].pppoe`. Через пять минут без свежего опроса статус и привязка теряют подтверждение. Доступность Интернета требует отдельного измерения.

Если тот же источник RouterOS сообщает состояние родительского Ethernet-интерфейса, `pppoe.parentLink` показывает линк с собственным временем измерения. Показание старше десяти минут скрывается. Оно относится к порту MikroTik. Порт провайдера требует отдельных сведений.

В `pppoe_internet_checks` можно указать до двух публичных IPv4-адресов для каждого ID WAN. Сборщик отправляет по одному ICMP-запросу с самого MikroTik через текущую PPPoE-сессию. В карточке и MCP каждая цель имеет отдельное показание. Ответ подтверждает доступность цели, отсутствие ответа оставляет её без подтверждения. Эти дополнительные проверки не меняют состояние самой PPPoE-сессии. [Параметры Ping RouterOS](https://help.mikrotik.com/docs/spaces/ROS/pages/8323183/Ping)

Если канонический контекст содержит одну датированную запись `observed_state.ipv4_interfaces` с совпадающим IPv4-адресом партнёра, карта добавляет имя его интерфейса и дату записи из GitHub. Это работает для транзитного адреса и для адреса управления, найденного через ARP и FDB MikroTik. Каждый результат показывается на своей стороне. Для физической пары по-прежнему нужны свежие данные с обоих концов.

Параметр `lan_bridge` в этой привязке добавляет наблюдение о пути к адресу управления партнёра. Карта сопоставляет свежий ARP адреса, динамическую запись MAC в мосту MikroTik и рабочее состояние одного найденного Ethernet-порта. В карточке указывается порт MikroTik и время наблюдения.

Для автоматического чтения Proxmox используйте HTTPS-имя, соответствующее сертификату, и токен с разделением привилегий. Файл токена содержит значение заголовка `PVEAPIToken=USER@REALM!TOKENID=SECRET`. Сборщику нужны права чтения узлов, списка ВМ и конфигураций ВМ для сопоставления MAC. Укажите файл доверенного CA, если его нет в системном хранилище.

Карточка кластера показывает ответ API, кворум и количество участников в сети по `/cluster/status`. При доступном API потеря кворума или участника даёт жёлтый статус. Если кворум или полный состав кластера не подтверждён и сбоев не обнаружено, статус серый. Состояние отдельного гипервизора показано в его карточке.

Для гипервизора в сети карточка показывает CPU, память, корневой раздел и время работы по `/cluster/resources?type=node`. В API и MCP поле `resources` содержит долю CPU, объёмы в байтах, время работы в секундах и время опроса. Устаревшие и недоступные показатели скрываются. Корневой раздел относится к ОС гипервизора.

Отдельный опрос `GET /nodes/{node}/status` проверяет доступное место `rootfs.avail` и заполнение swap. Доступный гипервизор становится жёлтым при остатке на корневом разделе не более 10% или заполнении swap от 90%. Подтверждённое отсутствие swap показывается как «Не настроен». Пропуск ответа или истечение пяти минут оставляет результат проверки без подтверждения. Свободная память показывается информационно. Если версия Proxmox передаёт `memory.available`, карточка показывает доступную память. API и MCP возвращают объёмы, статусы, пороги и время в `nodes[].resourceCapacity`.

В разделе «Физические диски» отображаются результаты `GET /nodes/{node}/disks/list`. API и MCP публикуют `hardwareDisks` с временем опроса, устройством, размером, состоянием SMART и оценкой остаточного ресурса, если Proxmox её предоставил. Серийные номера и WWN исключаются. Подтверждённая ошибка SMART переводит доступный гипервизор в жёлтый статус. Состояние логических хранилищ и томов требует отдельного источника.

В разделе «Пулы ZFS» отображаются состояние, ёмкость и свободное место из `GET /nodes/{node}/disks/zfs`. API и MCP публикуют `zfsPools` с временем опроса. Деградация или отказ пула переводят доступный гипервизор в жёлтый статус. Привязка ID хранилища ВМ к пулу требует конфигурации хранилищ Proxmox.

В разделе «Пулы LVM-thin» отображается заполнение данных и метаданных из `GET /nodes/{node}/disks/lvmthin`. API и MCP публикуют `lvmThinPools` с объёмами в байтах и временем опроса. Заполнение любого из двух компонентов от 90% переводит доступный гипервизор в жёлтый статус.

Для ВМ и контейнеров карта читает текущую конфигурацию дисков Proxmox. В API и MCP поле `guestStorage` содержит имя устройства, ID хранилища, размер по конфигурации в байтах и время чтения. Выключенная ВМ показывает эти данные, если её конфигурация доступна. В этот список входят диски и точки монтирования на хранилищах Proxmox. Ёмкость и доступность самого хранилища требуют отдельной проверки.

Карточка кластера группирует свежие назначения дисков по гипервизору и ID хранилища. API и MCP публикуют их в `storageAssignments` с количеством гостей и дисков и временем самой ранней конфигурации в сводке. Один ID хранилища может ссылаться на разные локальные пулы на разных узлах. Сводка опирается на конфигурации гостей и подтверждённое размещение в кластере.

В `hypervisor_management_bridges` укажите мост управления для каждого проверяемого гипервизора по имени узла Proxmox. Карта подтверждает оба порта соединения, когда Proxmox показывает активный мост с одним активным Ethernet-интерфейсом, адрес моста совпадает с инвентарём, а свежий ARP и подтверждённая таблица MAC указывают на один порт коммутатора. Для мостов с несколькими интерфейсами или агрегацией карта сохраняет имеющиеся данные о портах.

Для портов сети ВМ карта уточняет имя интерфейса гипервизора по активному мосту Proxmox. Требуются один активный Ethernet-интерфейс в мосту и свежая запись MAC запущенной ВМ на уже подтверждённом порту коммутатора. При неоднозначном сопоставлении сохраняются данные инвентаря.

Если MAC самой ВМ не наблюдался, карта может показать «Аплинк моста». Для этого нужен единственный активный Ethernet-интерфейс моста и свежая подтверждённая пара портов между гипервизором и коммутатором. Аплинк относится к конфигурации подключения ВМ. Наблюдение трафика ВМ отображается отдельной строкой «MAC ВМ замечен».

Если для этого интерфейса есть только подтверждённый путь по MAC-таблице, карточка ВМ показывает «Путь аплинка по MAC-таблице». В API наблюдение помечено `switchUplink.viaMacTable: true`. Подтверждение относится к пути от интерфейса гипервизора до порта коммутатора. Между ними могут находиться промежуточные устройства.

Запущенная ВМ QEMU отображается красной, если текущая конфигурация Proxmox показывает, что все её адаптеры отключены. Сборщик применяет этот результат при полном сопоставлении адаптеров и отсутствии проброса устройств, пользовательских аргументов QEMU и скрипта запуска. Состояние питания ВМ и подключение её адаптеров к мостам видны в карточке.

При свежем состоянии QEMU `prelaunch` карта показывает недоступную ВМ и причину «Гостевая ОС ещё не запущена». Блокировка Proxmox, например `backup`, отображается в карточке. Подключение адаптера к мосту видно по конфигурации, а наблюдение трафика гостя требует свежих сетевых данных.

Для LACP укажите в списке `lacp_links` источник SNMP (`source`), имя агрегата (`aggregate`), имена его портов (`members`) и узел-партнёр из сетевого контекста (`asset`). Сборщик проверяет принадлежность каждого порта к агрегату, рабочее состояние LACP с обеих сторон и соответствие MAC партнёра свежему ARP его адреса управления. В карточке показываются подтверждённые порты коммутатора и номера портов партнёра из LACP. Эти номера не раскрывают имена интерфейсов в ОС партнёра.

Карточка партнёра и MCP показывают резервирование LACP по каждому ожидаемому порту. Свежий статус down или административное отключение на коммутаторе переводит доступного партнёра в жёлтый статус. Для зелёного нужно подтверждение состояния LACP за последние пять минут и соответствие партнёра по ARP за последние восемь минут. В API используются `nodes[].lacpHealth` и `topologyAudit.lacpHealth`. В `portEvidence[].lacp.polledAt` указано время непосредственного опроса LACP.

В карточке связи состояние и скорость физического порта показываются отдельно от состояния и скорости агрегата. API и MCP возвращают показания физического порта в `portEvidence[].portStates`, агрегата в `portEvidence[].lacp.aggregateState`, номер порта партнёра в `portEvidence[].lacp.partnerPort`. Для показаний нужен свежий опрос SNMP.

Двустороннее LLDP подтверждает пару портов между коммутаторами, когда оба свежих объявления указывают друг на друга, MAC шасси однозначно сопоставляются со свежими ARP или SNMP, а на каждом порту наблюдается один сосед. Числовой псевдоним порта сопоставляется с `ifIndex` только при таком взаимном подтверждении.

Если таблица MAC показывает другое устройство за портом с подтверждённым соседом LLDP, карта сохраняет наблюдение о пути и снимает подтверждение этой пары портов. Двустороннее LLDP имеет приоритет при выборе соседа. Остальные подтверждённые порты той же связи остаются в карте.

Для уже проверенной пары портов коммутаторов из сетевого контекста запись `SNMP · двусторонний FDB` показывает совпадение схемы со свежими таблицами MAC и рабочим состоянием обоих портов. Запись исчезает, если один порт перестал отвечать условиям проверки или LLDP указывает на другого соседа. Таблицы MAC без проверенной схемы сохраняются как наблюдения о пути.

В карточке связи с названными портами видны свежие состояния каждого однозначно сопоставленного порта и время SNMP-опроса. Это наблюдение доступно и для предполагаемых пар. Статус «линк поднят» относится к конкретному порту. Подтверждение связи между устройствами определяется отдельно.

Для предполагаемой пары коммутаторов «SNMP · взаимные MAC» подтверждает путь через указанные порты. На каждом поднятом порту должен однозначно наблюдаться MAC управления другого коммутатора. Карта показывает путь пунктиром. Между портами могут находиться промежуточные устройства.

Сводку по портам возвращает `GET /api/v1/network/infrastructure?view=topology` и вызов MCP `openvpn_network_infrastructure` с `{"view":"topology"}`. `directLinks` считает связи по наиболее сильному подтверждению портов. `pending` показывает до 64 заявленных пар без подтверждения, включая порты на связях, где уже подтверждён другой порт. Для каждой пары доступны наблюдаемые пути между этими узлами через указанный порт. Путь по MAC-таблице остаётся наблюдением пути. Если в схеме указан агрегат LACP, учитываются подтверждённые участники агрегата. Для условного имени интерфейса Proxmox учитывается подтверждённое соединение с тем же портом коммутатора.

Карточка такого пути показывает предполагаемую пару из GitHub и сообщает, что прямое соединение ещё не подтверждено. Свежие наблюдения LLDP показывают число отдельных шасси. API и MCP возвращают его как `lldpChassisCount` в `ports[]` и `portEvidence[].portStates`. Поле `lldpNeighborCount` по-прежнему считает пары шасси и порта.

Запись MAC за портом без независимого подтверждения соседства сохраняется в API как наблюдение пути. В карточке такие наблюдения свёрнуты под «Неподтверждённые пути». Для пары, уже указанной в сетевом контексте, запись видна среди доказательств этой пары. Статус физического соединения определяется схемой и LLDP.

При расчёте подтверждённых подключений Netctl и при построении карты запись FDB и рабочее состояние интерфейса должны относиться к одному SNMP-опросу. Если в этом опросе интерфейс записан только по `ifIndex`, используется точное совпадение индекса из FDB. В сохранённом подтверждении сохраняется исходный ключ порта, а в доказательстве указывается ключ записи, из которой прочитано его состояние.

Если LLDP видит несколько шасси на одном порту или порт уже отмечен в контексте как общий, карта показывает «Путь через общий порт». Подтверждение требует одного наблюдаемого порта для шасси на этом коммутаторе, совпадения его MAC с одним устройством контекста и свежего состояния порта SNMP. Пунктир ведёт через этот порт. Физический порт на удалённом устройстве может оставаться неизвестным.

Если у маршрутизатора на общем порту MAC шасси отличается от контекста, путь может быть подтверждён по текущим наблюдениям. LLDP, ARP, обнаружение соседей MikroTik и запись хоста должны однозначно согласоваться по объявленному IP и MAC. Этот MAC и адрес не должны принадлежать другому устройству контекста. Расхождение остаётся в карточке, а время подтверждения ограничено самым ранним из использованных наблюдений.

Когда подтверждённое подключение MAC совпадает с проверенным портом в инвентаре, карта добавляет свежее наблюдение к существующей связи. Для такого узла в `asset_ip_checks` можно указать адрес из `observed_ipv4_addresses`. Ответ ICMP показывается в карточке как дополнительное наблюдение об адресе. Цвет узла определяется его собственной проверкой доступности.

Для маршрутизируемой цели `asset_ip_check_gateways` сопоставляет ID узла с ID ожидаемого шлюза из сетевого контекста. Сборщик сверяет маршрут ядра с `management_ip` шлюза и отправляет ICMP с выбранного ядром интерфейса и адреса. При расхождении шлюза запрос пропускается. API и MCP показывают маршрут и результат ICMP отдельно в `serviceChecks[].localRoute` и `serviceChecks[].state`.

Для рабочей станции с одним однозначным MAC карта читает сигнал присутствия Endpoint из локальной проекции инвентаря. Нужны подтверждённые привязки сети и агента, успешная проверка идентичности и свежий сигнал агента. В карточке видны источник и время. Сигнал заполняет неизвестную доступность узла, а сетевой ответ и порты отображаются отдельно. Отсутствие свежего сигнала оставляет доступность на основе других наблюдений.

Диагностика гостей Proxmox доступна в MCP с `{"view":"agents"}` и через `GET /api/v1/network/infrastructure?view=agents`. Она сопоставляет включённый сетевой интерфейс запущенного гостя с регистрациями Endpoint по MAC. Совпадение считается однозначным при одной регистрации на одного гостя. Состояние `online` требует свежих данных об интерфейсе и присутствии агента. Совпадения служат для проверки привязок, цвета карты определяются прежними источниками. MAC и идентификаторы регистраций в выдачу не входят.

Карточка ВМ запрашивает ту же диагностику при открытии и обновляет её, пока карточка открыта. Строка «Агент Endpoint» показывает время последней связи или причину отсутствия подтверждения. Данные доступны авторизованной сессии карты. Снимок карты загружается независимо от Endpoint.

Для неоднозначных совпадений MCP указывает причину в `agentAudit.guests[].reason`. Значение `duplicate_guest_mac` означает повторяющийся MAC в конфигурации Proxmox. `multiple_registrations` означает несколько кандидатов Endpoint, а `registration_matches_multiple_guests` означает, что один кандидат подходит нескольким ВМ. Карта не присваивает этим записям статус связи агента.

Сводка включает всех гостей текущего снимка. `unmatched` означает, что среди возвращённых регистраций Endpoint нет совпадения с пригодным MAC гостя. `notEligible` считает гостей, для которых сопоставление невозможно. В `reason` указывается состояние гостя, давность данных Proxmox или ограничение сетевой конфигурации. Если источник Endpoint недоступен, сводка возвращает `sourceState: unavailable`.

Для однозначно сопоставленной ВМ `contextProfiles` содержит время последнего отчёта о состоянии, сети и инвентаре, если эти отчёты есть в Endpoint Platform. Карточка ВМ показывает даты рядом со строкой «Агент Endpoint». Сбор для карты использует уже опубликованные отчёты. Время отчёта и время последней связи агента отображаются отдельно.

Если базовый отчёт не содержит MAC, можно указать `endpoint_device_id` в локальной записи `guests` после сверки идентификатора регистрации непосредственно на ВМ с рабочим Endpoint Platform. Сборщик допускает эту привязку только при свежем совпадении VMID и уникального MAC включённого интерфейса из Proxmox. При другом кандидате по MAC или совпадении регистрации с несколькими ВМ карта отмечает конфликт. API публикует `identitySource: verified_enrollment` и свежесть связи агента. Идентификатор регистрации остаётся в локальной конфигурации и снимке сборщика.

Для наблюдения на конкретном коммутаторе задайте в `asset_fdb_paths` имя источника SNMP по ID устройства. Карта показывает путь через один рабочий порт, на котором свежая таблица MAC видит MAC адреса управления из ARP. Общий порт нескольких устройств может быть частью пути. Такие наблюдения выводятся как «Путь по MAC-таблице».

Для подтверждённой пары порта доступа CSS326 и рабочей станции с уникальным MAC сборщик дополнительно проверяет линк и ищет MAC станции в таблице коммутатора. Положительный результат доступен пять минут в `ports[].endpointMac` и в `portEvidence[].portStates` для стороны коммутатора. Он содержит ID станции, MAC и время опроса. При несовпадении MAC или порта текущий результат не показывается. Основание физической пары указывается отдельно. [BRIDGE-MIB, RFC 4188](https://www.rfc-editor.org/rfc/rfc4188)

Для устройства с однозначным MAC в сетевом контексте можно добавить тот же адрес управления в `asset_ip_checks`. ICMP запускается после сверки адреса с ARP и свежей MAC-таблицей выбранного коммутатора. Положительный результат показывает доступность по методу `ICMP · ARP + FDB`. Карточка связи отображает счётчики и скорости измеренного порта за его интервал опроса. Это помогает проверить, на каком конце замечены ошибки или отбросы.

Для коммутатора с настроенным `asset_ip_checks` и MAC в инвентаре адресная доступность из Netctl учитывается при совпадении MAC. Активная проверка с подтверждением LLDP и ARP выполняется и после внесения адреса управления в канонический контекст.

Для службы из `asset_services` флаг `require_network_identity: true` требует однозначного MAC в контексте, свежей записи ARP и наблюдения на рабочем порту источника из `asset_fdb_paths`. Запрос выполняется только при совпадении IP настройки и подтверждённого адреса. API публикует время подтверждения `serviceChecks[].identityCheckedAt`. Если подтверждение отсутствует или устарело, результат недоступен для расчёта зелёного статуса.

Для службы, уже объявленной в сетевом контексте, укажите её ID в `asset_services` и тот же узел в `asset`. Название и размещение берутся из контекста. Если привязка расходится с контекстом, проверка пропускает запрос.

Список `downstream_mac_links` включает до 12 связей из сетевого контекста. Сторона `endpoint_a` задаёт порт опроса, `endpoint_b` задаёт коммутатор, в карточке которого показывается список. Поле `downstream.basis` содержит `lldp` для свежей пары портов LLDP или `reciprocal_mac` для двустороннего наблюдения MAC управления. При `reciprocal_mac` отображается путь, а подтверждение физического соединения берётся из отдельной записи о связи. Значение `inventory_stp` требует подтверждённую в инвентаре пару, оба рабочих порта и свежее наблюдение STP на нижнем коммутаторе. STP должен видеть мост верхнего коммутатора через указанный порт. Поле `stpCheckedAt` содержит время опроса STP. Такой набор показывает текущий путь MAC по ранее сверенной паре портов. Имена `Gi1/0/31` и `gigabitEthernet 1/0/31` сопоставляются при единственном совпадении в последнем сборе. Если есть LLDP и на аплинке виден известный MAC коммутатора, показываются остальные изученные MAC. В остальных случаях показываются только MAC, которые однозначно найдены в свежей FDB нижнего коммутатора на рабочем порту вне аплинка. Наблюдение с именем и временем порта доступно в `devices[].switchPort`. Оно подтверждает порт, на котором изучен MAC, включая путь через следующий коммутатор.

MAC сопоставляются с IP при однозначной свежей записи ARP, а доступность берётся из активных проверок Netctl. Если ARP-записи нет, до 16 свежих и однозначных адресов из Netctl проверяются ICMP по прямому маршруту UI_VPN и сверяются с MAC в состоянии REACHABLE в таблице соседей. В API и MCP доступны `nodes[].downstream` и `topologyAudit.downstreamSwitches`, до 256 MAC на коммутатор.

Если для того же гипервизора задан `hypervisor_management_bridges`, путь может показать и интерфейс на стороне Proxmox. Для этого адрес активного моста должен совпадать с адресом управления, а у моста должен быть один рабочий физический интерфейс. Отметка относится к пути и двум наблюдаемым портам. Прямое кабельное соседство подтверждается отдельно.

```bash
python -m app.infrastructure_collect \
  --context /srv/network_configuration/config/network-context.yaml \
  --schema /srv/network_configuration/schemas/network-context.schema.json \
  --git-revision "$(git -C /srv/network_configuration rev-parse HEAD)" \
  --server-health /var/lib/openvpn-web/server-observer/latest.json \
  --bindings /etc/openvpn-web/infrastructure/bindings.json \
  --proxmox-url https://proxmox.example.invalid:8006 \
  --proxmox-token-file /etc/openvpn-web/infrastructure/pve-token \
  --proxmox-ca /etc/openvpn-web/infrastructure/pve-ca.pem \
  --output /var/lib/openvpn-web/infrastructure/latest.json
```

Сборщик можно вызывать из системного таймера каждые пять минут. По умолчанию панель читает файл из примера. Другой путь задаётся через `INFRASTRUCTURE_MAP_SNAPSHOT_PATH`. Для разового импорта используется `--proxmox-export` с полями `at`, `cluster`, `nodes`, `guests` и `configs`, где последнее поле содержит конфигурации привязанных ВМ по VMID. При запуске от учётной записи с прямым доступом к netctl задайте `NETCTL_USE_SUDO=0`.
