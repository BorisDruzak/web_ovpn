# Сетевые проверки UI VPN

В меню **Сеть и диагностика → Сетевые проверки** можно проверить маршрут ядра VPN-сервера, рассчитать прямой путь от сетевого актива по данным RouterOS, запустить трассировку до наблюдаемого IPv4-узла и проверить связь с включённым источником Network Observer. В истории запусков видны назначение, время и результат для текущего оператора.

| Проверка | Что означает результат |
|---|---|
| `linux_route` | Маршрут, выбранный ядром VPN-сервера для IP-адреса. Команда `ip route get` читает решение ядра без отправки пакетов. |
| `asset_route` | Расчёт прямого пути, таблицы маршрутизации и применимых правил по собранным фактам RouterOS. При неполных или устаревших фактах результат `unknown`. |
| `trace_route` | Переходы, ответившие на трассировку от VPN-сервера. Запуск разрешён для IPv4-адреса из мониторинга, максимум 12 переходов и 18 секунд. Промежуточный узел может пропустить запрос, сохраняя пересылку трафика. |
| `source_test` | Результат штатной проверки `netctl sources test` для включённого источника. |
| `route_availability` | Матрица ответов по заданным источникам, путям и протоколам. Для RouterOS TTL=1 показывает первый ответивший маршрутизатор, если получен ICMP Time Exceeded. |
| `iperf3` | Скорость TCP между VPN-сервером и выбранным узлом. Профиль задаёт длительность и целевой темп iperf3. Результат около целевого темпа подтверждает, что участок выдержал заданную нагрузку. |
| `https_speed` | Скорость за полный HTTPS-запрос между VPN-сервером и Cloudflare. Результат содержит выбор маршрута ядром и фактический адрес источника. |
| `pcap_capture` | PCAP по указанному в профиле интерфейсу, адресу, порту и протоколу. Файл доступен инициатору 30 минут. |
| `loop_check` | Повторное перемещение MAC между портами одного VLAN за последний час. События STP вблизи перемещений повышают уверенность. |

## API и MCP

API использует Bearer-токен панели. Для чтения требуется `network:read`, для запуска проверки — `network:diagnose`.

| HTTP | MCP |
|---|---|
| `GET /api/v1/network/diagnostics/checks` | `openvpn_network_diagnostic_checks` |
| `POST /api/v1/network/diagnostics/checks` | `openvpn_network_run_check` |
| `GET /api/v1/network/diagnostics/runs?limit=20` | `openvpn_network_check_runs` |
| `GET /api/v1/network/diagnostics/route-runs?profile=wan-comparison&limit=20` | `openvpn_network_route_runs` |
| `GET /api/v1/network/diagnostics/interfaces?source=…&interface=…` | `openvpn_network_interface_history` |
| `GET /api/v1/network/diagnostics/loops?source=…` | `openvpn_network_loop_diagnostics` |
| `GET /api/v1/network/diagnostics/captures` | `openvpn_network_capture_list` |
| `GET /api/v1/network/diagnostics/captures/{capture_id}` | `openvpn_network_download_pcap` |

В **Сетевых проверках → История доступности по маршрутам** выберите профиль и интервал UTC. В REST API и MCP передавайте `profile`, `since` и `until`. Для времени укажите часовой пояс, например `2026-11-13T00:05:00+05:00`. Начальная граница включается, конечная исключается. Фильтры применяются до ограничения числа записей. История охватывает последние 14 дней и включает плановые запуски и ручные запуски текущего оператора.

Для маршрутизаторов с источником `mikrotik_api` история интерфейсов показывает прирост `rx-error`, `tx-error`, `rx-drop` и `tx-drop` между опросами. Пропуск означает, что для пары снимков нет пригодных показаний, например, после изменения `link-downs`, уменьшения счётчика или для записей, сделанных до начала сбора этих полей. Ноль означает, что счётчик за интервал не вырос. [Счётчики интерфейсов RouterOS](https://help.mikrotik.com/docs/spaces/ROS/pages/139526175/Interface%2Bstats%2Band%2Bmonitor-traffic)

В таблице истории интерфейса коммутатора рядом с ошибками и отброшенными пакетами показывается скорость широковещательного трафика за интервал между опросами. API и MCP возвращают её как `in_broadcast_pps` и `out_broadcast_pps`. При пропуске данных или сбросе счётчиков значение отсутствует. Поле `broadcast_coverage` содержит число пригодных интервалов и объясняет отсутствие измерений, например, если устройство не отдаёт `ifCounterDiscontinuityTime`.

Для CSS326 и поддерживаемых TP-Link коллектор читает `ifCounterDiscontinuityTime` пакетами по восемь `ifIndex` для портов с широковещательными счётчиками. Опрос ограничен 64 портами и пятью секундами на устройство. Для расчёта скорости по-прежнему нужны два последовательных замера с одинаковым маркером сброса.

На D-Link DGS-1210-52 F1 с ПО `6.20.007` счётчики IF-MIB оставались на нуле при наличии широковещательных кадров на парном порту SNR. История и проверка петель показывают `unreliable_counters` и пропускают расчёт скорости широковещания для этой версии. Сырые счётчики остаются в базе.

Если ключ порта менялся при сборе, история коммутатора объединяет записи с одинаковыми именем и SNMP `ifIndex`. Ссылка со старым ключом открывает историю этого порта, а API возвращает текущий ключ в `selected.key`.

История STP собирается на SNR и MikroTik CSS326 по BRIDGE-MIB. Для оценки возможной петли также нужна таблица MAC с идентификаторами VLAN. История STP CSS326 доступна, даже если устройство отдаёт MAC только через BRIDGE-MIB без VLAN.

Для вывода «признаков нет» нужны три последних опроса FDB в текущем окне, наблюдения MAC с VLAN и свежий STP. Если в одном из этих опросов часть записей FDB отброшена при разборе, охват считается недостаточным. Причина видна в UI и в `coverage.fdb.reason` через API и MCP.

Повторные перемещения между той же парой портов из FDB без VLAN доступны в `unclassified_mac_movements` через API и MCP и в строке коммутатора в UI. Эти наблюдения помогают выбрать порты для проверки. Оценка петли по-прежнему требует записи MAC с подтверждённым VLAN.

Для запуска передайте JSON с идентификатором проверки и её параметрами.

```json
{"check": "linux_route", "destination": "192.0.2.20"}
```

`asset_route` дополнительно принимает `asset_key`, `protocol` и `port` для TCP или UDP. `source_test` принимает `source`. Детали проверки возвращаются в `data.result`, код результата — в `data.status`. История содержит итог каждого запуска и идентификатор запроса. При отсутствии установленного `ip` или `tracepath` соответствующая проверка возвращает `unavailable`.

Для активных проверок действует общий интервал повторного запуска по оператору и типу проверки. В течение пяти минут повтор вернёт `rate_limited`.

## Доступность по маршрутам

В UI откройте **Сетевые проверки → Доступность по маршрутам**, выберите профиль и запустите сравнение. API и MCP принимают тот же идентификатор:

```json
{"check":"route_availability","profile":"wan-comparison"}
```

Профили задаются в секции `routes` файла `/etc/openvpn-web/network-probes.json`. Файл принадлежит root, защищён от записи службой и доступен на чтение пользователям `openvpn-web` и `netctl`. Профиль содержит до восьми проб. Оператор может запустить один профиль раз в пять минут. Таймер `openvpn-web-route-probes.timer` запускает до шести профилей с `scheduled: true` раз в пять минут. До четырёх из них могут использовать RouterOS или удалённые SSH-пробники. История за 14 дней содержит свои ручные и общие запланированные результаты. Если два соседних запланированных измерения одной пробы получили разные ответы на TTL=1, история показывает смену первого узла. Для двух соседних запланированных запусков с одинаковыми параметрами `probe_changes` сохраняет изменения статуса каждой пробы. Время события относится к проверке, которая заметила изменение.

- Для `router_source` укажите имя включённого источника Network Observer. RouterOS-проба отправляет три ICMP-пакета. При `expected_first_hop` отдельно отправляется один пакет с TTL=1. `path_status` отражает совпадение первого узла, расхождение или отсутствие наблюдения. Результат относится к исходящему трафику самого маршрутизатора. Для IPsec укажите `ipsec: true`, адрес источника из защищённой подсети и отдельную пробу в каждом направлении. Результат содержит состояние совпавшей политики и доступные общие счётчики SA между пирами. Счётчики охватывают весь трафик пары пиров.
- `interface` и `routing_table` передаются только для RouterOS. Поддержка `routing-table` зависит от версии. Если RouterOS отклоняет параметр, проверка возвращает `unavailable`. Для уже существующего правила policy routing можно использовать соответствующий адрес источника и назначение, проверяя первый узел. [Документация RouterOS Ping](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/ping/)
- Для непосредственно подключённого шлюза задайте `observe_neighbor: true` вместе с `router_source` и `interface`. На источнике RouterOS API проверка читает ARP-запись для точной пары IP и интерфейса после ping. `gateway_arp` описывает состояние записи отдельно от результата ICMP. [Документация RouterOS по ARP](https://manual.mikrotik.com/docs/getting-started/networking-fundamentals/)
- `rtt_variation` содержит среднее абсолютное изменение RTT между соседними по номеру ICMP-ответами и число пар. Пары через пропущенный пакет не учитываются. При трёх пакетах максимум две пары. Поле сохраняется в истории каждого запуска. [Пример вывода RouterOS ping](https://manual.mikrotik.com/docs/getting-started/first-time-configuration/)
- Для источника RouterOS API поле `trace_hops` от 2 до 8 добавляет трассировку к проверке с `expected_first_hop`. На каждый TTL отправляется один ICMP-запрос с теми же параметрами маршрута. История показывает ответившие переходы, пропуски и достижение цели. Трассировка разделяет общий лимит времени с основной проверкой.
- Для DNS укажите `dns_transport: "udp"` или `dns_transport: "tcp"`, чтобы проверить один транспорт. При явном UDP усечённый ответ считается неуспешным. Без этого поля проба начинает с UDP и повторяет запрос по TCP только при усечённом ответе. UI показывает выбранный транспорт и транспорт ответа. REST API и MCP возвращают их в `dns_transport` и `evidence.dns_transport`.
- Без `router_source` и `agent_origin` проверка стартует с VPN-сервера. Доступны ICMP, TCP, TLS, HTTP, HTTPS и DNS. `mtu` задаёт размер IPv4-пакета ICMP с DF. Для HTTPS укажите имя сертификата, для HTTP можно указать имя виртуального хоста. Для сертификата внутреннего удостоверяющего центра задайте абсолютный `tls_ca_file` на узле запуска. DNS-запрос идёт на заданный резолвер, поддерживает тип записи и сверку набора ответов. `kernel_route` хранит расчёт ядра с указанным адресом источника.
- Для пробы с клиентского VLAN или VPN-клиента укажите `agent_origin` управляемого Linux-узла. На узле должны быть Python с зависимостями пробника, ограниченная учётная запись SSH и тот же профиль с локальным экземпляром пробы без `agent_origin`. У локального экземпляра должны совпадать идентификаторы и параметры измерения. При расхождении проверка возвращает `unavailable` до отправки пакетов.
- В таблице запусков статус ответа, причина пробы и выбор маршрута ядром показаны раздельно. Тайм-аут SSH относится к связи с пробником. Тайм-аут DNS или ICMP относится к проверяемой цели. В REST API и MCP причины передаются в `evidence.reason`, а результат запроса маршрута — в `kernel_route`.

Конфигурация контроллера `/etc/openvpn-web/route-probe-origins.json` содержит `{"origins":{"probe-a":{"host":"192.0.2.50","user":"route-probe","port":22}}}`. В `/etc/openvpn-web/route-probe-ssh/` поместите проверенный `known_hosts` и выделенный ключ `probe-a.key` с режимом `0640`, владельцем root и группой службы. Используйте root-owned forced-command wrapper, который запускает `python -E -s -m app.network_route_remote` из каталога установки пробника. Ключ выделенной учётной записи ограничьте `restrict`, `from=` адресом контроллера и `command=` путём к wrapper. Для выполнения wrapper выделенной учётной записи нужна рабочая оболочка, а её вход по паролю должен быть закрыт.

Для ручного smoke-теста отдельной RouterOS-пробы используйте `netctl --json path probe --profile=<id> --probe=<id> --expected-config=<digest>`. Дайджест возвращает `RouteProbe.config_digest()` для записи из каталога, с которым запускается проверка. Через API и MCP он вычисляется автоматически.

После тайм-аута или недоступности Linux-проба может вернуть `evidence.linux_neighbor` с адресом, интерфейсом и состоянием соседа. Пробник читает только одну запись ядра для следующего узла или напрямую подключённой цели и не отправляет дополнительную ARP-пробу. `failed` означает неудавшееся разрешение соседа, `incomplete` — незавершённое, `not_cached` — отсутствие записи на момент чтения. Состояние соседа и ответ приложения оцениваются отдельно. Для удалённого источника обновите также код SSH-пробника.

У RouterOS-пробы шлюза с явным `source_address` отсутствие ICMP и разрешённого ARP запускает проверку адреса и состояния указанного интерфейса. `evidence.gateway_source` показывает, назначен ли ожидаемый IPv4, и может содержать состояние DHCP-клиента. `evidence.gateway_link` передаёт состояние интерфейса по флагам `running` и `disabled` RouterOS. Для активного Ethernet-порта однократный опрос также может вернуть согласованную скорость, дуплекс и состояние автосогласования. Скорость линка относится к физическому порту, пропускную способность измеряют отдельные пробы HTTPS и iperf3.

В истории маршрутов пометка «Конфигурация изменилась» означает, что состав или параметры сохранённых проб отличаются от текущего профиля. Пометка «Конфигурация не подтверждена» появляется, если профиль отсутствует в текущем каталоге или в записи нет отпечатка пробы. Результат в истории относится к параметрам того запуска.

REST API `GET /api/v1/network/diagnostics/route-runs` и MCP `openvpn_network_route_runs` возвращают этот статус в `configuration_status`: `current` при совпадении с каталогом, `changed` при отличии и `unconfirmed` при отсутствии профиля или отпечатка. Статус рассчитывается при чтении истории.

Для проверки от VPN-сервера до подключённого клиента в профиле укажите `openvpn_client` и ожидаемый адрес туннеля в `target`. Панель сверяет имя и адрес по текущей таблице сессий OpenVPN. При отсутствии подходящей сессии возвращается `not_connected`, а при недоступности таблицы — `unavailable`.

Для проверки **с клиента через туннель** задайте на контроллере `agent_origin`, `openvpn_client`, туннельный `source_address` и `expected_kernel_interface`. Контроллер сверяет туннельный адрес по живой сессии до вызова пробника, а пробник сверяет выбор интерфейса ядром до отправки пакета. В локальном профиле пробника опустите `agent_origin` и `openvpn_client`, остальные параметры измерения должны совпадать.

Для пробы с Linux или Windows укажите `expected_kernel_interface`, если перед отправкой пакета нужно проверить выбор интерфейса ядром. Например, для клиентского адреса OpenVPN задайте `tun0`. При другом интерфейсе или недоступном расчёте проба возвращает `unavailable` с причиной в `evidence.reason`. REST API, MCP и панель показывают ожидаемый интерфейс отдельно от выбора ядра.

Для маршрута через конкретный IPv4-шлюз задайте `expected_kernel_gateway`. При другом шлюзе или выборе маршрута напрямую без шлюза проба возвращает `unavailable` с причиной `kernel_gateway_mismatch` до отправки трафика. Если заданы оба параметра, ядро должно выбрать указанные интерфейс и шлюз. Фактический выбор доступен в `kernel_route.result`. Для подтверждения промежуточных узлов используйте трассировку.

Linux-пробник передаёт в расчёт ядра протокол и, для TCP и UDP, порт назначения. При усечённом ответе DNS по UDP пробник пересчитывает маршрут для TCP до повторного запроса. Если он выбирает другой интерфейс или шлюз, заданный в профиле, повторный запрос останавливается. Windows использует расчёт маршрута по адресам через `Find-NetRoute`.

Для Windows или другого источника без входящего SSH укажите `push_origin` и явный `source_address`. Команда `python -m app.network_route_spool measure <origin> <profile> --config <profile.json>` читает отдельный объект профиля с теми же определениями проб. Она выдаёт один JSON-результат в stdout. Отправьте его по SSH без удалённой команды и без TTY. На контроллере отдельный ключ и учётная запись принимают stdin только через `python -m app.network_route_spool receive <origin> <profile>`. Пара `origin` и `profile` закрепляется в forced command. Каталог `/var/lib/openvpn-route-probes/<origin>/` должен быть доступен на запись только приёмнику и на чтение веб-службе.

Приёмник SSH загружает секцию `routes` из каталога, поэтому изменения схемы замеров скорости и захватов не требуют его обновления. Панель читает один пакет с каждого пробника на запуск профиля и принимает измерения возрастом до трёх минут. Для планового запуска раз в пять минут можно передавать пакет каждую минуту. Метка «Замер на пробнике» и `evidence.origin_measured_at` относятся ко времени пакета на исходном узле, в том числе при устаревании. Ручной запуск профиля читает пакет и выполняет остальные пробы по запросу.

В разделе **IPsec** ошибка опроса видна в карточке источника. `GET /api/v1/network/ipsec` и `openvpn_network_ipsec` возвращают тот же отчёт с `sources[].status` и `sources[].errors`. Для ручной проверки `netctl ipsec status` сохраняет ненулевой код при отказе опроса. Ключ `--allow-source-errors` возвращает ноль при наличии сформированного отчёта.

В истории маршрутов `probes[].ipsec` хранит состояние подходящей политики отдельно от ответа ICMP. Панель показывает `phase2_count` из отчёта политики. Если опрос не дал данных, поле `reason` указывает, где он прервался. `ssh_connect_timeout` означает, что опрос не установил SSH-соединение с источником. `collector_timeout` означает, что весь вызов сборщика превысил лимит времени.

Для включённой туннельной политики с заданным локальным IPv4 источник RouterOS API также проверяет, назначен ли этот адрес. Поле `local_sa_address_status` доступно в политике IPsec и в истории маршрута. Оно различает назначенный адрес, отсутствующий адрес и невозможность проверить назначение.

## Скорость интернета по HTTPS

В **Сетевых проверках → Скорость интернета по HTTPS** выберите профиль и направление. API и MCP используют параметры `{"check":"https_speed","profile":"internet-default","direction":"receive"}`. Для отправки укажите `send`. Успешный замер сохраняет скорость, объём и длительность в истории оператора.

Для сравнения провайдеров задайте `expected_wan_interface` в профиле с наблюдением RouterOS. При подтверждённом выходе через другой интерфейс статус будет `wan_mismatch`. При отсутствии подтверждения статус будет `wan_unconfirmed`. Скорость сохраняется в обоих случаях. В `wan_observation` доступны ожидаемый интерфейс и, при подтверждении, наблюдаемый интерфейс NAT. Профиль с этой настройкой получает статус `measured` только при совпадении интерфейсов. Настройка проверяет фактический выход после замера. Выход выбирают действующие маршруты.

Поле `gateway_check` со ссылкой `{"profile":"central-wan","probe":"is74-gateway"}` запускает существующую RouterOS-пробу шлюза перед HTTPS. Она должна быть настроена для того же источника RouterOS и WAN-интерфейса, с явным исходным IPv4 и `observe_neighbor`. Если шлюз не ответил или проба недоступна, результат `wan_gateway_unavailable` сохраняет состояние шлюза в истории. HTTPS-запрос при этом не выполняется. Успешная проба шлюза разрешает передачу, а фактический WAN по-прежнему сверяется после неё.

Секция `https_speed` в каталоге профилей задаёт публичный IPv4 узла `speed.cloudflare.com` и объёмы передачи. Перед добавлением проверьте актуальный адрес сервиса. На VPN-сервере требуется curl версии 8.4 или новее для ограничения размера ответа. Замер отправляет один запрос с проверкой TLS, без прокси и переадресаций. Максимум составляет 10 МБ на загрузку, 5 МБ синтетических данных на отправку и 12 секунд на запрос. Скорость включает установку соединения и ожидание ответа. Выбор провайдера на следующем маршрутизаторе проверяется отдельно. [Сервис измерения Cloudflare](https://github.com/cloudflare/speedtest)

Пара `router_source` и `source_address` включает проверку WAN на настроенном источнике MikroTik API. После замера netctl ищет запись соединения с точными адресами и портами, проверяет src-NAT и ответ, затем сопоставляет адрес NAT с одним интерфейсом маршрутизатора. История хранит результат в `wan_observation`. Интерфейс или причина, по которой WAN не удалось подтвердить, видны рядом со скоростью в UI. Скорость передачи сохраняется при любом результате проверки WAN.

## Профили iperf3 и PCAP

Каталог читает `/etc/openvpn-web/network-probes.json`, принадлежащий root и доступный службе на чтение. Адреса и параметры команд задаёт администратор в этом файле. В API передаётся только ключ профиля и направление замера. Для iperf3 интервал повтора применяется отдельно к каждому профилю и направлению.

Когда ответ активной проверки имеет статус `rate_limited`, поле `result.retry_after_seconds` в REST API и MCP содержит остаток интервала с округлением вверх. Панель показывает это же значение. Для совместного теста PCAP и iperf3 дождитесь окончания интервала у обеих операций, запустите захват и выполните замер во время захвата.

```json
{"check":"iperf3","profile":"lan-test","direction":"receive"}
```

```json
{"check":"pcap_capture","profile":"lan-test-tcp"}
```

Образцы находятся в `deploy/network-probes.json.sample` и `deploy/ui-vpn-iperf-peer.service.sample`. Перед запуском слушателя укажите адрес управляемого узла, порт и разрешённый IPv4-адрес VPN-сервера. Проверьте ограничения systemd на живом соединении с разрешённого и другого узла. Для VPN-сервера установите пакеты `iperf3` и `wireshark-common`, оставив стандартный слушатель iperf3 выключенным.

При отказе TCP до начала передачи панель повторяет подключение к слушателю один раз в пределах общего тайм-аута. Успешный результат после повтора содержит `preconnect_retries`.

Для замера с конкретного локального адреса задайте `source_address`. `bind_interface` дополнительно привязывает соединение к интерфейсу Linux. До отправки тестового трафика панель запрашивает у ядра маршрут с учётом адреса источника, интерфейса и порта TCP. В результате видны ответ ядра и адреса потока из отчёта iperf3. Если адреса отчёта расходятся с профилем, скорости не сохраняются. Для проверки выбора провайдера на следующем маршрутизаторе нужна отдельная точка наблюдения. [Документация iperf3](https://software.es.net/iperf/invoking.html)

История новых успешных замеров iperf3 сохраняет скорости отправителя и получателя, целевой темп, число повторных передач TCP и, когда источник задан в профиле, выбранный ядром маршрут и адреса соединения. Панель показывает скорости, повторные передачи и выбор ядра. Полная запись доступна в `GET /api/v1/network/diagnostics/runs` и `openvpn_network_check_runs`. У старых записей остаётся прежний статус замера.

Для управляемого приёмника за пределами LAN в профиле iperf3 можно указать `router_source`, `source_address` (IPv4) и `expected_wan_interface`. MikroTik сопоставляет адреса и порты TCP-потока данных из отчёта iperf3 с записью NAT. Панель, REST API и MCP сохраняют скорости вместе с `wan_observation`, в том числе при `wan_mismatch` и `wan_unconfirmed`. Для приёмки WAN передайте наблюдаемый интерфейс MikroTik в `--speed iperf3 PROFILE INTERFACE`. Для обычного профиля LAN укажите интерфейс ядра VPN-сервера.

Профиль iperf3 может ссылаться на пробу шлюза через `gateway_check`, как профиль HTTPS. Проба должна относиться к тому же источнику RouterOS и ожидаемому WAN-интерфейсу. При недоступности шлюза замер не запускается. История сохраняет `wan_gateway_unavailable` и доступные сведения о DHCP, линке и ARP.

На Ubuntu ограничьте запуск `dumpcap` группой `openvpn-capture` и выдайте файлу capability `cap_net_raw=ep`. Drop-in `deploy/network-probe-capture.conf` подключает эту группу к веб-службе и создаёт каталог PCAP с режимом `0700` в `/run`. После обновления пакета перепроверьте права и capability `dumpcap`.

Захват сохраняет первые 96 байт каждого совпавшего кадра. В зависимости от длины заголовков в эти байты может попасть начало полезной нагрузки. В рабочем профиле используется тестовый поток iperf3. Для захвата прикладного трафика используйте защищённый HTTPS-доступ к панели. MCP сохраняет скачанный файл в локальный каталог `.codex/network-captures`. Серверная копия удаляется при истечении срока или перезапуске службы. Скачанная копия остаётся у оператора.

Проверка петли использует FDB и STP. При наличии счётчиков IF-MIB она также показывает среднюю частоту широковещательных пакетов на портах события за перекрывающиеся интервалы опроса. Вход и выход отображаются отдельно. Выходной счётчик включает пакеты, запрошенные к отправке. Интервалы с разрывом счётчика, сменой интерфейса или перезапуском оборудования пропускаются. Оценка петли по-прежнему опирается на FDB и STP. [IF-MIB (RFC 2863)](https://datatracker.ietf.org/doc/html/rfc2863) · [Список проверок перед приёмкой](network-diagnostics-acceptance.md)

Если среди трёх последних опросов FDB есть сбой, REST API и MCP возвращают причину `failed_fdb_poll`, а панель показывает её в колонке охвата. Для оценки об отсутствии признаков петли нужны три новых пригодных опроса и актуальные данные STP. Сохранённые перемещения MAC остаются в отчёте.

Если новый опрос STP завершился ошибкой или вернул неполный снимок, API и MCP показывают `failed_stp_poll` вместе со временем последнего успешного наблюдения. Панель отмечает, что сохранённое состояние STP требует подтверждения.
