# Приёмка сетевой диагностики

Из корня репозитория запустите `python -m deploy.verify_network_diagnostics` с переменными подключения OpenVPN Control `OPENVPN_WEB_BASE_URL` и `OPENVPN_WEB_API_TOKEN_FILE` или `OPENVPN_WEB_API_TOKEN`. Для проверки установленной копии MCP добавьте `--mcp-script` с путём к её `openvpn_mcp_server.py`. Скрипт читает OpenAPI, сравнивает каталоги REST API и MCP, сверяет состав и свежесть плановых результатов и выводит статусы проб в JSON. Поле `route_overview` содержит общую сводку, сверенную между REST API и MCP. Она охватывает все плановые профили, в том числе при фильтре `--route-profile`. Для каждого планового профиля `run_id` указывает проверенную запись, а `api_matches` показывает, совпала ли запись с тем же ID в REST API, включая результаты всех проб. `loop_diagnostics.source_coverage` содержит свежесть FDB и STP, число пригодных интервалов широковещательных счётчиков и признаки усечения по каждому коммутатору.

Код `0` означает, что контракты доступны и свежие плановые результаты и данные L2 совпали в REST API и MCP. Поле `loop_diagnostics.api_matches` показывает результат сверки L2. Границы окна вычисляются заново для каждого запроса. При отличии наблюдений скрипт повторяет оба запроса один раз. Код `1` означает ошибку проверки, отсутствие свежего результата или расхождение результатов. С параметром `--require-reachable` код `2` означает, что один или несколько маршрутов с актуальными данными недоступны. Допустимый возраст результата по умолчанию составляет 10 минут и задаётся параметром `--max-age-minutes`.

Для каждого планового запуска скрипт сравнивает `config_digest` каждой пробы с текущим каталогом. Поле `configuration_matches` показывает совпадение. Если, например, изменились назначение, источник, таблица маршрутизации или параметры протокола, дождитесь планового запуска с новой конфигурацией. До него скрипт возвращает `1`, даже если предыдущий результат ещё свежий.

Повторяемый параметр `--route-profile PROFILE` ограничивает чтение истории и строгие проверки маршрутов выбранными плановыми профилями. Например, `--route-profile vlan50-transit --require-reachable --require-dns-transport` проверяет доступность и DNS на VLAN50. Скрипт по-прежнему сверяет весь каталог и отчёт L2. Если выбран неизвестный или только ручной профиль, JSON перечисляет такие имена, а код возврата равен `1`.

Флаг `--require-expected-first-hop` проверяет все выбранные плановые пробы с настроенным `expected_first_hop`. В JSON видны ожидаемый и наблюдаемый узлы, статус совпадения и итоговые счётчики `expected_first_hops`. Код `2` означает, что хотя бы один ожидаемый первый переход не подтверждён. Если ожидаемые переходы отсутствуют в выбранных профилях, скрипт возвращает `1`. Для проверки первого перехода и ответа цели в одном запуске укажите оба флага. Смена ожидаемого узла в каталоге требует свежего запуска с новой настройкой.

Для проб с трассировкой поле `trace` содержит измеренные переходы с TTL, адресом и временем ответа, включая позиции без ответа, и причину завершения. Например, `partial` с причиной `hop_limit` означает, что трассировка остановилась на заданном числе переходов. Доступность самой цели отражена в отдельном статусе пробы.

Если ICMP-проба вернула статистику, в отчёте есть число отправленных и полученных пакетов и доля потерь. При наличии измерений выводятся минимальный, средний и максимальный RTT, а также среднее абсолютное изменение между последовательными ответами и число сравниваемых пар. При отсутствии ответов поле RTT отсутствует.

Флаг `--require-expected-kernel-interface` проверяет плановые пробы с настроенным `expected_kernel_interface`. Скрипт сверяет настройку каталога с сохранённым запуском и показывает фактический интерфейс, статус расчёта ядра и результат проверки сессии OpenVPN, если он есть. Для пробы с привязкой к клиенту нужны подходящая сессия и совпавший интерфейс. Код `2` означает, что хотя бы один интерфейс не подтверждён. Код `1` означает отсутствие таких проб или расхождение каталога и истории. Ответ цели проверяется флагом `--require-reachable`.

Флаг `--require-dns-transport` проверяет плановые DNS-пробы с явно заданным UDP или TCP. Для успеха нужны совпадение заданного и фактического транспорта, статус `reachable`, ответ `NOERROR` и совпадение записей, если в профиле заданы ожидаемые записи. В JSON блок `dns_transports` содержит число настроенных и подтверждённых проб. Код `2` означает, что хотя бы одна проба не подтверждена. Код `1` возвращается при отсутствии таких проб в каталоге или несовпадении настроенного транспорта в каталоге и истории.

Флаг `--require-http-status` проверяет плановые HTTP- и HTTPS-пробы. Каждая цель должна ответить ожидаемым кодом из текущего каталога. По умолчанию ожидается HTTP 200. В JSON видны ожидаемый и полученный коды и итог `http_probes`. Код `2` означает, что хотя бы одна HTTP-проба не подтверждена, код `1` — что в выбранных профилях таких проб нет или проверка не смогла сверить историю. Для приёмки всех протоколов профиля добавьте `--require-reachable`.

При наличии данных скрипт выводит в каждой пробе причину результата `reason`, состояние линка `gateway_link`, назначение исходного адреса и состояние DHCP `gateway_source`, результат ARP `gateway_arp`. Если ожидаемый IPv4 отсутствует, действующая DHCP-аренда может добавить `dhcp_address` и `dhcp_gateway`. Для IPsec выводятся состояние политики, число Phase 2, наличие локального адреса SA и причина сбоя опроса. Эти поля берутся из той же плановой записи, что и статус пробы. [DHCP-клиент RouterOS](https://manual.mikrotik.com/docs/network-management/dhcp/client/)

Флаг `--require-ipsec` проверяет все плановые пробы с `ipsec: true`. Успех требует ответа цели и политики в состоянии `established` с положительным числом Phase 2. Если опрос явно показал отсутствие локального адреса SA, политика не засчитывается. В JSON блок `ipsec_probes` отдельно показывает подтверждённые политики, доступные цели и пробы, выполнившие оба условия. Для отдельной пробы `ipsec` показывает селекторы найденной политики или число совпадений при неоднозначном результате. Если маршрутизатор вернул счётчики SA, `peer_sa_counters` показывает число ассоциаций и байты по направлениям для пары IPsec-адресов. Один такой счётчик может включать трафик нескольких политик. Код `2` означает неподтверждённую пробу, код `1` — отсутствие настроенных IPsec-проб или расхождение каталога и истории.

Флаг `--require-bidirectional-ipsec` требует встречные пробы в одном профиле. Адрес источника одной пробы должен быть целью другой, а маршрутизаторы запуска должны различаться. Для каждого направления нужны ответ цели и подтверждённая политика с Phase 2. Код `1` означает, что встречной конфигурации нет хотя бы для одной пары. Код `2` означает, что пробы настроены, но двусторонний обмен не подтверждён. Подробности по адресам и точкам запуска доступны в `bidirectional_ipsec`. Для архива добавьте `--route-profile archive-ipsec`.

Флаг `--require-loop-coverage` требует, чтобы для каждого коммутатора были свежие наблюдения FDB с VLAN и STP без усечения. `loop_diagnostics.coverage` показывает число источников с достаточными данными, число источников в отчёте и полноту охвата. Код `2` означает неполный охват, код `1` — отсутствие источников или ошибку проверки. Выявленные признаки петли по-прежнему описывает `loop_diagnostics.status`. Широковещательные счётчики остаются дополнительным наблюдением.

Флаг `--require-broadcast-coverage` проверяет наличие хотя бы одного пригодного интервала широковещания на каждом коммутаторе. Усечение выборки широковещания или списка источников делает охват неполным. Итог в `loop_diagnostics.broadcast_coverage` показывает число коммутаторов с пригодными интервалами. Код `2` означает неполный охват, код `1` — отсутствие источников или ошибку проверки. Покрытие конкретных портов смотрите в `loop_diagnostics.source_coverage`.

Флаг `--require-loopback-vlan SOURCE VLAN` проверяет покрытие конкретного VLAN штатным детектором. Можно указать его несколько раз. Свежесть наблюдения задаёт `--max-age-minutes`, результаты появляются в `loopback_vlan_checks`. Код `0` подтверждает покрытие независимо от срабатываний. Поле `detected` содержит `true` при срабатывании, `false` при его отсутствии в полном списке и `null`, когда определить это нельзя. Код `2` означает, что покрытие не подтверждено, код `1` — что источник отсутствует или произошла ошибка проверки. Охват FDB и STP по-прежнему проверяется флагом `--require-loop-coverage`.

Параметр `--capture-id UUID` проверяет уже сохранённый непустой PCAP того же оператора. Скрипт сравнивает запись в списках REST API и MCP, скачивает файл через оба интерфейса и сверяет содержимое, размер и число пакетов. В отчёте `capture` сохраняются ID, число пакетов, размер и SHA-256. Код `1` означает, что файл отсутствует, истёк, пуст или не прошёл сверку. MCP оставляет копию в штатном каталоге `.codex/network-captures`. Для проверки соответствия пакетов фильтру профиля используйте Wireshark или tcpdump.

Повторяемый параметр `--interface SOURCE NAME` сверяет идентификатор интерфейса, число доступных точек и до 300 последних интервалов REST API и MCP. В `interfaces` видны время последнего наблюдения и суммы ошибок и отброшенных пакетов по пригодным интервалам. Если ни в одном интервале счётчик не доступен, его сумма равна `null`. При расхождении или устаревшем последнем наблюдении скрипт возвращает `1`.

Повторяемый параметр `--speed CHECK PROFILE INTERFACE` проверяет последние сохранённые замеры текущего оператора в обоих направлениях. Сначала выполните замеры через REST API или MCP. Примеры параметров: `--speed iperf3 lan-test ens18` и `--speed https_speed internet-default ether9_wan_RTK`. Для iperf3 скрипт сверяет адреса соединения и интерфейс ядра. Если запись iperf3 содержит наблюдение WAN, требуется подтверждённый интерфейс MikroTik по NAT, как и для HTTPS. Отчёт показывает результат каждого направления и его совпадение с REST API. Пропущенный, устаревший или неподтверждённый замер возвращает код `1`. Ответы `rate_limited` и `busy` не считаются замерами.

Если в истории замера есть сведения о WAN, отчёт `--speed` включает `gateway_check` со статусом шлюза, DHCP, линком и ARP, а также `wan_observation` с результатом сверки NAT. Эти поля доступны и при неподтверждённом замере.

Для автоматической проверки пакетов добавьте `--require-capture-filter` к `--capture-id UUID`. На машине, где запущен скрипт, нужен `tcpdump` в `PATH`. Скрипт передаёт скачанный PCAP локальному tcpdump и проверяет, что каждый пакет соответствует протоколу, адресу и порту профиля в одном из двух направлений. Успешный отчёт содержит `outside_filter_packets: 0`.

## Доступность и маршруты

При накоплении просроченных `host_observations` команда `netctl --json retention prune-host-observations --limit 10000` удаляет просроченные строки в пределах одной порции, используя тот же срок хранения 30 дней. Для следующей порции передайте `--after-id` со значением `next_after_id` из результата. `null` означает конец таблицы. Порция освобождает блокировку сбора после фиксации. В 08:38 по Екатеринбургу восемь порций удалили 80 000 записей, каждый вызов занял от 0,50 до 0,67 секунды. Для остальных таблиц действует штатная очистка.

В 08:39–08:43 ещё 120 порций удалили 1 200 000 просроченных наблюдений. Очистка дождалась завершения планового сбора в 08:40 и продолжила с прежней позиции. Сбор обновил 10 из 11 источников.
