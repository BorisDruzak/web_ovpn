# План безопасной интеграции расширенного профиля ALT Linux

## Цель и границы

Вернуть в `main` результаты ветки `codex/alt-resilience-integration`, но не
переносить её целиком. Ветка содержит 68 собственных коммитов против 27
собственных коммитов `main` и изменяет 127 файлов. Она добавляет не только
роли установки ПО, но и новый контракт контроллера, bootstrap, очереди и
сценарий первого доменного входа.

Целевая область — **настройка уже установленной ALT Linux**. Установка с ISO
не меняется. Текущий ручной путь через `workstationctl configure` сохраняется
как основной до отдельного решения о включении автоматической оркестрации.

## Подтверждённый состав отложенной ветки

- Базовый доменный профиль: Plasma, DNS/SSSD, join AD, GPO, проверка.
- Прикладной профиль `core-apps`: Яндекс Браузер, ONLYOFFICE, Nextcloud и
  ярлыки.
- Защищённый профиль: корпоративные и российские CA, CryptoPro, CAdES,
  плагин Госуслуг и Endpoint Agent.
- Удалённый доступ: только KRFB для назначенного доменного пользователя;
  XRDP, RustDesk и AnyDesk в ветке отсутствуют.
- Отдельный post-login сценарий и восстановление профиля Яндекс Браузера.
- Изменения устойчивости bootstrap/контроллера: структурированные результаты,
  классификация ошибок, блокировки и systemd-таймеры.

Проверка `git diff --check main...codex/alt-resilience-integration` проходит.
Это проверка формата diff, а не доказательство работоспособности на ALT.

## Целевой порядок выполнения

```text
уже установленная ALT
  -> bootstrap и регистрация (без изменения доверия)
  -> SSH / preflight / ручный configure request
  -> этап 03: базовая ОС + AD + GPO
  -> этап 03: выбранные системные компоненты
  -> контролируемая перезагрузка, если нужна
  -> первый вход назначенного AD-пользователя
  -> этап 04: ярлыки и KRFB только для этого пользователя
  -> отдельный операторский запуск: миграция профиля Яндекс Браузера
```

Системные компоненты не должны требовать существующего домашнего каталога AD
пользователя. Всё, что пишет в `/home/<AD-user>`, допускается лишь после
успешного интерактивного доменного входа и проверки владельца каталога.

## Этап 0 — зафиксировать совместимый базовый контракт

**Зависимость:** выполняется первым; без него перенос `03` из ветки
интеграции несовместим с текущим `ConfigureRequest`.

1. Сохранить текущий ручной JSON-контракт в
   `deploy/alt-linux/control/alt_deploy/configure.py`: обязательные поля
   домена, hostname и явный `vars-file`.
2. Добавить поля `software_profile` (`base` / `core-apps`) и
   `remote_access_profile` (`none` / `krfb`) как обратносуместимые опции:
   старый ручной запрос должен означать `base` и `none`, а не отвергаться.
3. Для `core-apps` и `krfb` требовать `assigned_domain_user`, но не принимать
   пароль и не записывать его в логи или результаты.
4. Ввести результат этапа 03 с фазой, признаком повторяемости ошибки,
   компонентами и `reboot_required`. Контроллер читает только строго
   проверенный JSON и сохраняет безопасный код ошибки.
5. Согласовать длительность запуска: расширенный этап 03 допускает до 90
   минут; текущая обработка таймаута должна возвращать безопасный `run_id`.

**Проверки:** unit-тесты `ConfigureRequest`, успешный старый ручной request,
ошибочный request с неразрешённым профилем, timeout и невалидный result JSON.
До переноса ролей выполнить `ansible-playbook --syntax-check` для 03 на
ALT-контроллере.

## Этап 1 — перенести базовую рабочую станцию и устойчивость AD

**Зависит от этапа 0. Не зависит от прикладных артефактов.**

Перенести и адаптировать к текущему `main`:

- `plasma_baseline`, `domain_login_baseline`, улучшения
  `manual_preflight`, `prejoin_upgrade`, `workstation_network`,
  `domain_join`, `domain_verify` и GPO-ролей;
- task-файлы `configure_critical_phase.yml` и
  `configure_finalize.yml`, чтобы ошибка сохранялась до завершения запуска;
- проверки устойчивости пакетов, DNS/KDC и повторного domain join.

В `03-configure-domain-workstation.yml` критическая последовательность должна
остаться такой:

1. preflight и hostname;
2. upgrade и перезапуск SSH-сессии при необходимости;
3. базовые пакеты, GPO prerequisites, DNS/NTP;
4. join/проверка AD;
5. GPO client и базовая проверка домена;
6. Plasma baseline;
7. запись структурированного результата и только затем перезагрузка, если
   она требуется.

**Проверки:** идемпотентный повтор stage 03 на пилотной машине, отсутствие
перезагрузки в середине роли, `realm list`, `id <test-user>`, `gpupdate`,
DNS/KDC и результат configure. Откат — вернуть предыдущую версию
playbook/контроллера из резервной копии control plane; не удалять computer
object вручную без отдельной диагностики.

## Этап 2 — прикладной профиль `core-apps`

**Зависит от этапов 0–1. Включается только явным `software_profile=core-apps`.**

Перенести роли `software_browser`, `software_onlyoffice`,
`software_nextcloud_desktop` и `desktop_shortcuts`. Ярлыки в `/etc/skel`
разрешены на системном этапе; запись в домашний каталог пользователя — нет.

Перед переносом необходимо отдельно сверить каждый контроллерный artefact из
`group_vars/all.yml`: абсолютный путь, владелец, режим, SHA-256, RPM name/EVR
и архитектура. Указанные в исторической ветке SHA-256 — это инвентарные
ожидания, а не подтверждение, что файлы сейчас существуют на контроллере.

**Проверки:** checksum до установки, `rpm -q` с ожидаемым EVR, запуск
исполняемых файлов, наличие desktop entries. Если artefact отсутствует или
хеш не совпадает, компонент должен завершиться понятной ошибкой без частичной
установки и без продолжения профиля как успешного.

## Этап 3 — доверие и обязательные защитные компоненты

**Зависит от этапов 0–2 и от подготовленного защищённого хранилища artefacts.**

Перенести `organization_ca`, `software_cryptopro`,
`software_cryptopro_cades`, `software_gosuslugi_plugin` и
`endpoint_agent_alt` отдельным набором.

- CA устанавливаются до HTTPS-взаимодействий Endpoint и проверяются по
  fingerprint/хешу.
- Лицензия CryptoPro, Endpoint claim и токены остаются только в Vault или
  защищённой среде исполнения (`no_log`); они не попадают в Git, result JSON
  или вывод CI.
- Endpoint Agent можно включать только после согласования gateway URL, CA,
  жизненного цикла claim и канарейки. Нельзя переносить исторические
  идентификаторы кампании как действующие значения без проверки владельца и
  срока действия.

**Проверки:** тесты статических контрактов, checksum/RPM verification,
краткоживущий claim с редактированным логом, работа службы агента и
независимая проверка TLS цепочки. Канарейка — одна тестовая машина; при
ошибке остановить rollout и отозвать только созданный для неё claim.

## Этап 4 — профиль первого доменного входа и KRFB

**Зависит от этапов 0–3 и от фактического первого входа пользователя.**

Перенести отдельный `04-configure-domain-user-profile.yml`,
`desktop_shortcuts_user` и `remote_access_krfb`.

Этап 04 запускается только после того, как `getent passwd` вернул назначенного
пользователя, а его `/home/...` существует, является каталогом и принадлежит
его UID/GID. Он создаёт защищённый `krfbrc`, autostart и пользовательские
ярлыки. Пароль KRFB не читается для проверки и не выводится.

Перед включением нужно подтвердить отдельным сетевым решением: источник
подключений, маршрут/VPN и firewall для VNC/TCP 5900. Наличие роли не означает
разрешение открыть порт в сети. Никакие XRDP/RustDesk/AnyDesk роли при этом не
добавляются.

**Проверки:** новый AD-пользователь создаёт home только при реальном входе,
`04` идемпотентен, файлы имеют нужных владельцев/режимы, KRFB доступен лишь по
утверждённому сетевому пути. Откат — удалить только сгенерированные
пользовательские конфиги/автозапуск после подтверждения пользователя; не
удалять домашний каталог.

## Этап 5 — автоматическая оркестрация первого входа (не включать по умолчанию)

**Зависит от этапа 4; выходит за текущий ручной MVP.**

Только после успешной ручной канарейки рассмотреть перенос:

- capture/validation `assigned_domain_user` в bootstrap и
  `00-validate-assigned-domain-user.yml`;
- `process_pending.py`, `reconcile_first_login.py` и systemd timer;
- статусы `awaiting_first_domain_login`, `configuring_user_profile`, `ready`,
  `degraded`, `failed`.

Эта часть должна быть feature-flagged и выключена в `main` по умолчанию. Она
не должна создавать AD home, повторять domain join или превращать отсутствие
первого логина в отказ настройки системы.

## Этап 6 — миграция профиля Яндекс Браузера

**Независимая операторская операция после этапа 2; не часть первичной
настройки.**

Перенести launcher и `yandex_profile_restore` лишь после утверждения политики
переноса пользовательских данных. Архив должен иметь manifest, READY-marker и
SHA-256; браузер останавливается штатно; замена профиля делается через staging
и обратимый backup. Нельзя включать миграцию автоматически в stage 03/04.

## Порядок коммитов и приёмка

1. `refactor(alt): align manual configure profile contract`
2. `feat(alt): harden base domain workstation profile`
3. `feat(alt): add verified core applications profile`
4. `feat(alt): add verified security workstation components`
5. `feat(alt): configure selected domain user profile`
6. `feat(alt): add optional first-login orchestration`
7. `feat(alt): add guarded yandex profile migration`

Перед каждым коммитом: актуальный diff, `git diff --check`, точечные pytest
для затронутого контроллера/Ansible assets и Ansible syntax check на
ALT-контроллере. Перед развёртыванием: резервная копия control plane, одна
канарейка, затем журнал результата и явно подтверждённый переход к следующей
машине. Изменения разворачиваются на `ui-vpn-deploy` только после отдельного
запроса пользователя.
