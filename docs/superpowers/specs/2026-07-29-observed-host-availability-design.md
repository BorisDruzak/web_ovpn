# Наблюдаемый мониторинг доступности и исторические устройства

## Цель

Плановый ICMP/TCP-мониторинг проверяет только известные устройства, а не все
пригодные адреса включённого CIDR. Список устройств по умолчанию показывает
только свежие наблюдения, но оператор может посмотреть исторические записи и
явно оставить конкретное старое устройство под мониторингом.

## Канонический контекст

`central-lan` с `192.168.100.0/23` разделяется в каноническом
`network_configuration` на два активных сегмента: `central-lan-100`
(`192.168.100.0/24`) и `central-lan-101` (`192.168.101.0/24`). Все ссылки
`management_segment` устройств переносятся по их management IP. В web-панели
никакой CIDR не вводится: после импорта новой ревизии оператор включает оба
новых stable ID обычной настройкой мониторинга.

## Набор плановых целей

Для включённого IPv4-сегмента планировщик формирует дедуплицированный набор:

1. IP существующих host records, у которых `last_seen_at` не старше 24 часов;
2. IP устройств с management-адресом в активном каноническом контексте;
3. IP с включённым явным force-monitor, пока запись не отключена оператором.

Источник наблюдения остаётся ARP/DHCP/bridge/FDB; старые исторические IP без
force-monitor не пингуются. Проверки остаются ICMP-first с настроенным TCP
fallback, принадлежат только включённому каноническому сегменту и не принимают
CIDR, порт или IP от браузера. Метрики availability run означают число
реальных проверенных целей, а не размер адресного диапазона.

## Список устройств и время

`/network/hosts` получает server-validated query-параметр периода:
`1h`, `24h` (по умолчанию), `7d`, `30d` или `all`. Он фильтрует отображение
по `last_seen_at` относительно времени запроса. Период не меняет набор
плановых probes, кроме постоянных force-monitor записей.

При периоде 7d, 30d или all старая запись остаётся видимой, но её статус
публично отображается как «данные устарели»; она не становится `online` или
`offline` без свежего активного результата. На странице явно показываются
`Last seen`, время активной проверки и её origin. История не сбрасывается
при выпуске функции: период считается от текущего времени и сохранённого
наблюдения конкретного устройства.

## Принудительный мониторинг

В карточке существующего исторического host record внутри включённого сегмента
появляется «Принудительно мониторить». Действие:

1. серверно проверяет существование host record, IPv4 и включённый канонический
   сегмент;
2. сохраняет явную per-host запись force-monitor без срока истечения;
3. запускает probe этого одного IP и штатный полный refresh наблюдений;
4. записывает отдельный audit-результат для успеха, busy, запрета и ошибки.

Force-monitor сохраняется, пока оператор не нажмёт «Отключить принудительный
мониторинг». В UI видны время включения, последний active evidence и состояние
последнего refresh. Действия включения, отключения, probe и refresh требуют
аутентификации, CSRF, одного принятого действия на actor/action за пять минут
и collection lock для полного refresh. Нельзя создать force-monitor для
произвольного или отсутствующего IP.

## Ошибки и тесты

- Если не удалось найти свежих или force-managed целей, run успешен с нулём
  целей и не публикует фиктивный offline для CIDR.
- Ошибка одного target не заменяет последнее полное доказательство CIDR.
- Busy refresh не отменяет уже сохранённый force-monitor и отображается явно.
- Тесты покрывают выбор observed/static/forced целей, исключение старых IP,
  дедупликацию, периоды списка, честный stale UI, force-monitor security и
  canonical split `central-lan`.
