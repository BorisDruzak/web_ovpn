# ALT Workstation: сетевые папки, OnlyOffice и Nextcloud Desktop

## Цель

Добавить в профиль доменной ALT Workstation три независимые возможности:

1. доступ всех доменных пользователей к существующей сетевой папке
   `\\antares\Public` через AD GPO;
2. установку утверждённого настольного клиента OnlyOffice через Ansible;
3. установку клиента Nextcloud Desktop через Ansible для всех рабочих станций.

## Границы

- Сценарий ручной установки, bootstrap, managed ISO и существующий domain join не
  изменяются.
- Сетевые папки не монтируются из Ansible, `/etc/fstab` не меняется.
- Ansible не создаёт AD-пользователей, не управляет правами на SMB-ресурсе и не
  содержит пользовательских паролей, токенов Nextcloud или SMB-учётных данных.
- В область не входят MyChat, Zabbix, принтеры, Consultant, IFCPlugin, прежние
  маршруты и старый механизм удалённого доступа.

## Архитектура

### Сетевая папка

Ответственность за подключение `\\antares\Public` остаётся у Windows AD. В
GPMC создаётся отдельная пользовательская политика `Network Drive - Public`,
привязанная к корню `sosnadmin.local` и применяемая к `Authenticated Users`;
она содержит только пользовательские настройки, поэтому компьютерные объекты
не получают карту диска.
Она применяется ко всем доменным пользователям независимо от OU их учётных
записей и не затрагивает компьютерные объекты или сервисные учётные записи.
В политике создаётся отображаемый сетевой диск с именем `Public`, путём
`\\antares\Public` и действием `Обновить`.

ALT-клиент уже получает `gpupdate` и `alterator-gpupdate` в существующей роли
`alt_group_policy_client`. Механизм ALT "Подключение сетевых дисков" создаёт
управляемое autofs-подключение для пользователя. Ожидаемая доступная точка
после пользовательского входа: `/run/media/<username>/drives`; для удобства
в этой же пользовательской GPO включается ссылка `~/net.drives`.

Ansible ограничивается проверкой, что GPO-клиент включён. В результате
configure не утверждается, что папка доступна: конечная проверка выполняется
после первого доменного входа пользователя и применения пользовательской GPO.

### OnlyOffice

Создаётся роль `software_onlyoffice`. Она принимает только controller-side
артефакт, описанный в `software_catalog.onlyoffice`: фиксированный путь,
SHA-256, ожидаемые имя пакета, EVR и архитектура. До установки роль проверяет
хеш и RPM metadata; затем копирует RPM во временный каталог цели, устанавливает
его через `apt-get -y install`, проверяет установленный EVR и удаляет временные
данные в `always`.

Путь, хеш, имя и версия задаются только после передачи утверждённого RPM.
Запрос configure не может переопределять ни один из этих параметров. Роль
возвращает только `onlyoffice_ok` и `onlyoffice_version`; содержимое RPM и
какие-либо секреты в public result не попадают.

### Nextcloud Desktop

Создаётся роль `software_nextcloud_desktop`. Для ALT используется системный
пакет `nextcloud-client`, устанавливаемый из утверждённого репозитория ALT
посредством APT. Роль обновляет metadata пакетов, устанавливает пакет при
отсутствии и проверяет установленный EVR и существование исполняемого файла
клиента. Плановые обновления этого репозиторного пакета выполняются отдельно
в согласованном системном обновлении, а не скрыто в configure.

Серверный URL, учётная запись, пароль, refresh-token, папка синхронизации и
автозапуск пользователя не настраиваются. После первого доменного входа
пользователь запускает клиент и авторизуется сам. Роль возвращает только
`nextcloud_desktop_ok` и `nextcloud_desktop_version`.

## Порядок configure

Роли приложений выполняются после `plasma_baseline`, `organization_ca`,
`software_cryptopro`, `software_cryptopro_cades` и
`software_gosuslugi_plugin`, но до `standard_software` и `domain_verify`:

```text
... → software_gosuslugi_plugin
    → software_onlyoffice
    → software_nextcloud_desktop
    → standard_software
    → remote_access_krfb
    → domain_verify
```

`domain_verify` публикует только безопасные логические результаты.

## Ошибки и идемпотентность

- Отсутствующий или несовпадающий OnlyOffice RPM останавливает configure до
  копирования на станцию с `ALT_PREFLIGHT_FAILURE:onlyoffice_artifact_invalid`.
- Несовпадение имени, EVR или архитектуры RPM останавливает выполнение с
  `ALT_PREFLIGHT_FAILURE:onlyoffice_rpm_metadata_invalid`.
- Недоступность пакета Nextcloud в утверждённых репозиториях либо невыполнение
  установки останавливает configure с обычной ошибкой APT; версия не
  подменяется неутверждённым локальным файлом.
- Повторный configure не переустанавливает уже соответствующие OnlyOffice и
  Nextcloud Desktop.
- Неудача пользовательской GPO не маскируется Ansible: диагностика выполняется
  через `gpupdate --target User` и журналы gpupdate от имени вошедшего
  пользователя.

## Приёмка

1. На контроллере `ansible-playbook --syntax-check` проходит для основного
   playbook.
2. `configure preview` перечисляет установку OnlyOffice и Nextcloud Desktop.
3. Первый запуск на одном пилотном ПК устанавливает оба приложения и содержит
   положительные безопасные result-поля.
4. Повторный запуск не меняет пакеты.
5. После входа доменным пользователем `\\antares\Public` доступен через
   автоподключение GPO, пользователь может создать и прочитать тестовый файл в
   пределах уже назначенных серверных прав.
6. Клиент Nextcloud запускается, но до интерактивного входа не содержит
   настроенной учётной записи или токена.

## Необходимые входные данные до запуска реализации

1. Один утверждённый RPM OnlyOffice, который будет положен на controller в
   каталог артефактов; из него будут получены и закреплены SHA-256, package
   name, EVR и архитектура.
2. Доступность `nextcloud-client` в активном репозитории ALT 11.x на
   контроллере и пилотной станции.
3. Проверка DNS-имени `antares` с пилотной ALT-станции и существующих SMB ACL
   для доменных пользователей до включения GPO.
